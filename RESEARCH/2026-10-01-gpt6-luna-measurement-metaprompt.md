## 3. 후보와 비교 연결을 먼저 오프라인으로 완성하라

조사 보고서의 후보 블록을 출발점으로 삼아 B를 하나만 만든다. 공용 한국어/근거/주입 방지 규칙, 기존 JSON 필드와 배열 상한, 분야별 관점, 사실/추론/미확인의 구분을 유지한다. 문장 수는 편집 목표로 두고 지표 정의, 성립 조건과 중요한 미확인 정보 충족을 우선한다.

평가자용 정답, 정답 위치 힌트, 과거 reviewer 코멘트와 논문별 실패 정답을 생성 지시문에 넣지 않는다. 제공 PDF의 내용과 원문 표기는 정상 입력이다. B를 고정한 뒤 본 비교 중에 수정하지 않는다.

기존 `luna_compare.py`는 모델 비교용이며 프롬프트 변형 선택 옵션이 없다. 지원하지 않는 CLI 인자를 만들어 사용하지 말고, 기존 `invoke_product`, `RequestGate`, `RequestSpec`, 예산 원장과 write-once 기록을 재사용하는 최소 연결을 구현한다. 실험 프로세스 안에서만 프롬프트를 선택하고 운영 프롬프트는 유지한다. 조건 ID는 요청 key, campaign, 설정과 결과 파일에서 충돌 없이 구분한다.

기존 `RequestGate`로 실제 제품 함수가 구성한 요청을 생성 직전에 포착한다. 후보 적용을 확인하고 두 조건의 PDF, 모델, effort, wire schema, cap, 입력 경로가 같음을 검사한다. 요청에서 의도된 차이는 프롬프트 문구와 그 파생 hash다. 별도의 간소화된 입력으로 우회해서 제품 실측이라고 부르지 않는다.

작은 오프라인 검사 하나로 다음을 확인한다: A가 기존 지시문을 쓰고 B가 후보를 쓰며, 두 실행이 서로 오염되지 않고, 조건 ID가 충돌하지 않으며, 생성 API는 호출되지 않는다. 수정한 실행기에 기존 관련 검사도 수행한다.

완료 조건: `prompts/baseline.txt`, `prompts/v1.txt`, prompt/diff/hash, 12개 요청 계획과 설정 비교, 오프라인 검사 결과가 저장돼 있다. 이 단계에서 token-count API도 호출하지 않는다.

## 4. API 실행 권한과 비용을 확인하라

현재 세션에서 이 비교 cohort에 적용되는 명시적 새 지출 상한과 호출 범위를 확인한다. 과거 실험의 승인이나 `--run-paid-approved-usd-1` 플래그를 새로운 실측 승인으로 간주하지 않는다.

기존 도구의 `--mode dry-run`은 `responses.input_tokens.count`를 호출한다. 오프라인 준비와 구분하고 count API의 사용 조건과 비용도 사전 자료에 포함한다.

다음 자료를 제시한 뒤 필요한 API 실행 승인을 받는다: 12회 생성과 count 요청 수, 모델별 최신 공식 단가의 확인일/출처, 입력 추정, 출력 상한, cache-write와 해당 tier/장문/지역 요율을 반영한 예약 비용, 과거 누적 지출, 미정산 예약, 남은 한도. 추정 입력으로 계산했다면 추정임을 표시한다.

승인 후 동일 요청을 count하고 전체 남은 cohort 비용을 재산정한다. 한도를 넘으면 유료 종속 작업만 멈추고 완료된 준비 자료와 부족액을 인계한다. 기존 실행기의 USD 1 제한을 임의로 풀지 않는다. 다른 한도가 승인되면 해당 승인과 원장 정책에 맞는 최소 변경을 명시하고 검증한다.

API 키/인증 헤더와 개인 데이터는 산출물에 넣지 않는다. 원본 PDF 전체를 로그로 중복 복사하지 말고 안전한 파일 참조/hash와 요청 설정을 보존한다.

## 5. 승인된 실측을 수행하고 모든 시도를 기록하라

각 요청은 발행 전에 비용을 예약하고, 완료/실패 후 사용량으로 정산한다. timeout, incomplete, malformed, 미정산 요청을 삭제하거나 성공 응답으로 대체하지 않는다. 불명 비용은 0원이 아니다. 승인 없는 재시도를 발행하지 않는다.

최소 기록 항목:

- paper ID, condition ID, repeat, source/PDF hash, prompt/hash, app/wire schema hash, request fingerprint, 실제 제품 입력 경로.
- 요청/반환 모델, SDK, effort, cap, 제공 부록, 완료 상태와 incomplete reason.
- 입력, cached read, cache write, 출력, reasoning tokens, 사용량 완전성, 비용 산정 상태와 실제 tier.
- 원응답, 파싱 결과, 형식 검사, 오류와 예약/정산 기록.
- 호출 시작부터 응답/사용량 수신까지의 시간, count/대기/전체 작업 시간은 별도 정의.

출력 tokens에 reasoning이 이미 포함되면 비용에 다시 더하지 않는다. application cache와 provider cache를 혼동하지 않는다. API 응답을 받았다는 사실만으로 과학 검증 완료를 표시하지 않는다.

완료 조건: 계획된 각 요청에 완료 또는 명시적인 실패/미실행 상태가 있고, 원응답과 모든 발행 시도가 원장에 연결돼 있다.

## 6. 원문으로 블라인드 판정하라

응답의 A/B 라벨, 모델/가격/시간을 가린 검토 pack을 만들고 순서 seed를 고정한다. 가능한 경우 생성 프롬프트를 작성한 실행자와 다른 검토자가 원문으로 판정한다. 자기 검토만 수행했다면 독립 검증 미완료로 표시한다. 자동 reviewer의 점수는 원문 판정을 대신하지 않는다.

현재 6편 기준의 필수 항목과 허용 판정을 비교 전에 고정한다. 주요 서술뿐 아니라 strengths/weaknesses, 비교, 절별 설명, 적용 제안의 새 사실도 확인한다. 인용문 존재와 그 인용문이 주장을 지지하는지를 따로 본다. 수식은 가능한 경우 독립 검산을 사용한다.

| 지표 | 판정 방법 |
|---|---|
| 엄격 논문 PASS/FAIL | 기존 필수 기준을 모두 충족하고 새 사실/출처 결함도 없어야 PASS |
| 사실 지지율 | 원문이 지지하는 평가 대상 주장 수 / 평가 대상 주장 전체 |
| 필수 정보 충족률 | 정확히 포함된 사전 필수 항목 수 / 고정한 필수 항목 전체 |
| 출처 정확성 | 주장을 실제로 지지하는 claim-ref 연결 수 / 출력된 claim-ref 연결 전체 |
| 중요 미확인 정보 | 필요한 미확인 사항과 범위를 정확히 밝히는지, 원문에 있는 사실을 부재로 바꾸지 않는지 |
| 중대 오류 | 수치/단위/부호/방향/지표 정의/비교 대상/실물-시뮬레이션 범위 오류 수 |
| 형식/완료 | JSON, required 필드, 중복 키, 응답 상태, cap 도달 여부 |

분모와 주장 분해 규칙을 비교 전에 고정한다. 평가 대상이 0개인 비율은 N/A로 두고 정보 누락을 따로 표시한다. 출처를 출력하지 않은 답변을 출처 정확성 100%로 처리하지 않는다. `not_reported`로 사실 설명을 회피한 답변도 충족률에서 검사한다. 비적용 판정은 연구 유형과 고정 기준에 근거해야 한다.

각 실패에 생성 문구, 원문 위치와 짧은 근거, 실패 유형/심각도, 해당 기준을 연결한다. 낮은 심각도의 출처 결함과 큰 허위 사실을 같은 환각으로 합산하지 않는다. 종합 PASS/FAIL과 진단 지표는 함께 보존한다. 판정과 파일 hash를 고정한 뒤 A/B를 공개한다.

## 7. 추가 실험은 별도 조건으로 수행하라

1차 결과는 논문당 1쌍의 관측이다. 일반적 속도 우세나 안정성으로 주장하지 않는다. 추가 승인과 잔액이 있으면 두 번 더 전체 6쌍을 반복해 총 3쌍/논문으로 만들고, 다음 반복의 A/B 순서를 반대로 한다. 성공한 논문만 골라 반복하거나 최초 응답을 교체하지 않는다.

추가 reviewer, effort/cap/캐시 변경은 각각 별도 조건과 예산이다. 기존 audit pilot은 5.6 Luna의 검증 미완료 실험이므로 6 Luna 검토 효과의 증거로 쓰지 않는다. reviewer 실험에서는 원문 판정 기준의 false pass/false fail과 추가 비용/시간을 측정한다.

일반화나 제품 적용을 주장할 때는 개선에 사용하지 않은 논문을 별도 고정하고 평가한다. 실제 체인 통합은 동일 upstream 원문/설정에서 별도로 수행한다. 단독 deep_dive를 전체 앱 검증으로 표시하지 않는다. GUI 확인은 저장된 결과의 근거 링크/지표/모델/비용을 원기록과 대조한다.

필수 제출물은 비교 계획, A/B 프롬프트와 diff/hash, 요청/원응답/원장, 블라인드 원문 판정, 논문별 비교 CSV, 최종 보고서다. 성공/실패/미실행을 전부 포함한다.

비용 감소율은 `1 - sum(cost_B) / sum(cost_A)`로 계산하고 사용량/요율이 불명인 항목이 있으면 확정 감소율을 보류한다. 시간은 대응 쌍별 `time_B/time_A`의 중앙값, 범위와 반복 수를 보고한다. 실패 요청의 비용/시간과, 결과를 얻은 쌍만의 비교 범위를 함께 공개한다. 동일 원문 문구와 A/B 설명을 연결해 개선과 퇴보 사례를 보여준다.

최종 판정은 아래 중 증거에 맞게 선택한다.

- `awaiting_paid_approval`: 오프라인 준비 완료, 새 API 실측 승인 대기.
- `comparison_incomplete`: 예산/계정/실패 등으로 계획된 비교 또는 원문 판정 미완료.
- `no_clear_gain`: 비교 완료, 확인 가능한 개선 없음.
- `regression_gate_passed`: 기존 6편의 엄격 기준 통과. 운영 승격이나 미사용 논문 검증을 뜻하지 않는다.
- `candidate_failed`: 고정한 품질 게이트 미달.

판정 우선순위는 승인 대기, 비교 미완료, 후보 품질 게이트 미달, 기존 6편 게이트 통과 순서다. 준비/비교가 완료된 B가 품질 게이트에 미달하면 `candidate_failed`로 판정하고 부분 개선은 진단 지표와 사례로 함께 보고한다. `no_clear_gain`은 추가 실험의 조건 비교에 개선 근거가 없을 때 사용한다.

사전 품질 기준을 결과에 맞춰 바꾸지 않는다. 형식 통과, 긴 답변, reviewer의 동의, 저렴한 비용만으로 과학 정확성이나 운영 승격을 선언하지 않는다. 결론에는 재현 방법, 관측 범위, 남은 실패와 결론이 무효가 되는 조건을 간결하게 설명한다.
