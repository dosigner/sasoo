# Sasoo 분석 품질 후속 구현 메타프롬프트

너는 Sasoo의 분석 파이프라인과 과학적 결과 검증을 맡은 개발자다. 아래 범위의 실제 수정과 검증을 완료하라. 기존 병렬 실행 구조, 포인트별 분석, 설명의 상세함과 모델/effort 선택을 유지하면서 원문 근거 전달, 재현 조건 누락, HTML 입력 검사와 표시 결함을 개선한다.

작업 위치는 `/Users/dongj/dev/논문_사수_개발중`, 앱은 `sasoo/`다. 실제 파일 경로와 가장 구체적인 AGENTS.md를 먼저 확인하라. 한국어 경로의 NFC/NFD 차이를 고려하라.

## 1. 먼저 확인할 근거와 작업 경계

다음 문서를 먼저 읽고, 현재 코드와 달라진 부분을 확인하라.

1. `docs/validation/2026-10-11-parallel-analysis-next-steps.md`: 작업 순서, 확인한 원인, 수정 후보.
2. `docs/validation/2026-10-11-parallel-analysis-live.md`: 실제 API/설치 앱/워커 검증의 관측 결과와 한계.
3. `docs/validation/assets/parallel-live-20261011/quality-review.md`: recipe 누락과 원문 페이지 근거.
4. 그림 수식 작업에서는 같은 폴더의 `image-addendum.md`, HTML 작업에서는 `html-evidence.json`과 `generated-interactive.html`을 읽는다. 요청 전달을 조사할 때만 `ledger.jsonl`에서 관련 요청/응답 파일을 찾아 읽는다.

시작할 때 git 상태와 해당 파일의 변경 내용을 확인하고, 이미 진행 중인 사용자 변경을 보존하라. 수정할 공통 함수의 호출부, 테스트, API 계약, 캐시와 export 소비처를 먼저 파악하라. 기존 구현과 설치된 의존성을 재사용하고, 변경 범위를 좁게 유지하라.

`parallel-live-20261011/`의 원장, 원문 실응답, 이미지와 소스 스냅샷은 기존 평가 증거다. 이를 수정하거나 덮어쓰지 말고, 회귀 테스트에 필요한 자료는 새 작업 폴더에 복사하라. 임시 경로는 현재 존재 여부를 확인하고, 사라졌으면 저장된 소스 아카이브와 해시를 기준으로 별도 위치에 복원하라. 사용자 라이브러리와 설치 앱은 검증용 복사본으로부터 격리하라.

이번 실행의 기본 범위는 아래 2~4절의 구현/오프라인 검증과 5절의 유료 검증 준비까지다. 별도로 명시된 새 유료 호출 승인이 있을 때만 승인된 논문, 호출 수, 예산 안에서 5절을 실행하라. 이전 평가의 남은 예산은 새 평가의 승인으로 간주하지 않는다. 유료 승인이 없어도 독립적으로 진행할 수 있는 구현과 검증은 끝내라. 커밋, push, 공개 배포는 별도 지시가 있을 때 수행한다.

## 2. 표시와 HTML 입력 검사를 먼저 수정

관련 코드는 `frontend/src/lib/synthesisBlocks.ts`, `components/HtmlVisualization.tsx`, 해당 테스트와 그림/표 metadata 소비처다. 현재 위치와 호출 관계는 다시 확인하라.

- 값에 포함된 단위를 다시 붙이지 않도록 공통 formatter를 수정한다. `60%`와 `%`가 `60%%`가 되는 사례를 해결하고, 다른 단위가 우연히 같은 문자로 끝나는 경우에도 단위 경계를 보존한다. 원본 저장값은 유지한다.
- 필수 숫자 입력은 빈 문자열/공백을 숫자로 바꾸기 전에 검증한다. 선택 입력에 기본값을 적용한다면 그 정책을 명시한다. 범위를 벗어난 값과 vector 차원 불일치도 처리한다.
- HTML 검사에 빈 입력 사례를 추가하고, 입력별 출력 변화 또는 의도된 불변을 확인한다. 한 입력이 문서 일부를 바꿨다는 이유로 모든 입력을 통과시키지 않는다. 수학적으로 정상적인 상수 출력은 오류로 오인하지 않는다.
- 계산이 무효해졌을 때 이전 출력이 새 입력의 정상 결과처럼 보이지 않게 한다. sandbox, CSP, nonce와 메시지 출처 검증을 유지한다.
- 원문 전체의 그림/표 개수와 앱이 추출한 개수를 구분한다. 일부 본문만 본 screening의 `has_figures=false`는 논문 전체에 그림이 없다는 확정값으로 사용하지 않는다. metadata 불일치를 없애려고 DB 행 수나 기준값을 임의로 바꾸지 않는다.

완료 기준: 기존 중복 단위 및 빈 t fixture가 수정 전 실패/수정 후 통과하는 회귀 검사를 갖는다. 의도된 상수 출력, 유효한 기본값, 단위 경계의 반례도 확인한다. 실제 화면과 export에서 같은 의미를 표시하며 기존 자료를 다시 생성하지 않는다.

## 3. 그림/HTML 생성 단계에 필요한 원문 근거 전달

관련 경로는 `backend/services/analysis_execution.py`의 `_generate_single_paperbanana`, `_generate_single_html`, `services/document_context.py`, `services/viz/figure_gen.py`의 `_plan_description`이다.

확인된 원인은 다음과 같다. 수치가 빠진 그림의 요청에는 실제 Table 1 값이 없었고 설명 모델은 빈칸을 지시했다. `ψ_t=Gaussian density` 오기는 이미지 모델에 전달하기 전 설명문에 이미 존재했다. HTML 독립 요청에도 해당 식의 원문 구간이 빠져 있었다. 이 사실을 저장된 요청으로 재확인하라.

- 계획이 참조하는 표의 값, 수식, 변수 정의, 적용 조건과 원문 위치를 기존 context/PDF 근거에서 찾아 해당 요청에 전달한다. 앞부분 문자열만 자르는 현재 방식의 손실을 수정한다. 관련 없는 전체 자료를 무조건 덧붙이는 방식으로 해결하지 않는다.
- 과학적 내용과 그림의 배치 설명을 구분하고, 확인한 식과 값을 후속 설명 단계에서도 추적할 수 있게 한다. 원문 근거가 부족한 정량 그림은 그 이유와 상태를 남긴다.
- 정확한 수식 표현에는 기존 `EquationChain`/KaTeX를 활용한다. 이미지에 수식을 포함해야 하는 항목은 설명문과 렌더 결과의 검증 범위를 각각 명시한다. 표의 수치는 확인된 데이터로 렌더링하는 기존 경로를 우선 검토한다.
- HTML의 독립 변수, 파생 변수, 식의 평가 위치를 명확히 한다. `u_t(x0)`와 `u_t(ψ_t(x0))`는 다른 계산이다. 제공되는 검산 사례는 원문의 적용 조건과 일치해야 한다.

완료 기준: 저장된 Table 1 회귀 사례의 요청 payload에 필요한 값과 원문 위치가 실제로 들어간다. flow map과 density의 혼동이 검증에 드러난다. HTML은 경계값과 대표 입력에서 독립 계산과 대조한다. 생성 성공, 실행 성공, 원문 정확성을 각각 기록한다. 논문 고유 수치나 식을 일반 제품 로직에 하드코딩하지 않는다.

## 4. recipe의 누락과 미보고 판정 검사

관련 경로는 `_run_recipe`, `services/evidence_verifier.py`, `services/evidence_repo.py`, recipe 테스트와 표시 코드다. 기존 검사기는 출력된 parameters의 인용/페이지/값을 확인한다. 이 검사만으로 steps와 missing_info의 주장이나 누락된 조건까지 검증됐다고 판단하지 않는다. Recipe는 PDF 체인을 이어받으므로 이번 누락을 단순 입력 잘림으로 단정하지 않는다.

- 전처리/정규화, 입력 분포와 sampling, 학습 target/loss, 평가식과 단위 보정, solver/허용오차를 분야와 논문 유형에 맞게 점검한다. 해당 없는 항목은 적용 대상으로 강제하지 않는다.
- “원문에서 확인하지 못함”과 “저자가 보고하지 않음”을 구분한다. 원문에 있는 내용을 missing_info로 분류하는 충돌을 검증 대상으로 삼는다. 검색 결과가 없다는 사실만으로 부재를 확정하지 않는다.
- 기존 근거 검사기를 유지하고, 검증하지 못한 항목은 그 상태를 표시한다. 변경한 프롬프트나 모델의 자기평가만으로 누락이 해결됐다고 판정하지 않는다.
- Flow Matching 회귀 사례에는 `t~U[0,1]`, `x/128−1`, density/BPD 보정과 `+7`, 학습 target, 미보고 σ_min을 포함한다. 원문 부록과 식에서 독립적으로 정답 기준을 확보한다.
- 현재 단계와 로컬 검증 경로에서 해결 가능한 범위를 먼저 구현한다. 매 분석에 추가 유료 검토 모델을 붙이는 설계가 필요하면 비용/지연과 대안을 별도로 제시한다.

완료 기준: 원문에 있는 조건의 누락이나 잘못된 미보고 판정이 회귀 검증에서 드러난다. 확인되지 않은 σ_min/학습 seed는 임의로 채워지지 않는다. 기존 포인트별 분석과 근거 설명을 유지한다. 기존 17개 deep_dive 필드, 절별 답변 12개, 적용 조건 검사 8개는 이 저장된 회귀 사례의 기준이며 모든 논문의 고정 출력 개수로 사용하지 않는다.

## 5. 검증과 유료 실행 경계

각 수정은 실제 실패 자료에서 출발하고, 구현을 그대로 되풀이하지 않는 테스트로 확인하라. 프로젝트가 정한 적절한 백엔드 검사와 프런트엔드 타입 검사/린트/빌드를 수행한다. 앱 화면은 대표 데스크톱 크기에서, 생성 HTML은 좁은 화면에서도 실행해 console, 오류 상태, 입력/출력, overflow를 확인한다. 화면 값 최소 하나를 원문 또는 독립 계산과 대조한다. mock/fixture 검증과 실제 공급자/설치 앱 검증의 범위를 분명히 보고한다.

캐시 변경은 해당 프롬프트/근거 입력/검증 버전에 연결한다. 전역 버전 변경으로 모든 기존 분석을 다시 생성하는 일을 피하고, 기존 성공 결과와 비용 기록은 보존한다. 새 요청이 필요한 변경은 명시적 재분석 경로에서 수행한다.

오프라인 검증 이후 새 유료 승인이 있다면:

- 비교할 소스/입력/모델/effort를 고정한다. 속도 비교에는 같은 시각화 계획과 항목 수를 사용하고 실행 순서를 교차한다. 캐시 적중과 작업량 차이를 별도로 기록한다.
- 계산 중심, 실험/정량 중심, 리뷰 논문의 작은 대표 묶음을 선정한다. 품질 비교는 원문과 익명화한 결과만 받은 별도 검토자가 수행한다.
- 새 실행 ID와 요청별 원장을 사용한다. 발행 전에 예산을 예약하고, 사용량을 확인해 정산한다. 과거 성공 요청/중단 runner를 재실행하지 않는다. 새 생성 평가와 과거 요청의 재발행을 구분한다.
- 실패/시간 초과/비용 불명은 그대로 보존한다. 청구 상태가 불명확하면 추가 발행을 멈추고 회복 가능한 응답/사용량부터 확인한다. 실제 사용량과 청구서 확인 여부를 구분한다.

새 유료 승인이 없다면 코드 수정, 회귀 검사, 실제 GUI 확인을 마친 뒤, 새 평가 대상/예상 호출 수/보수적 예산/중단 기준을 검토 가능한 형태로 제시한다. 미실행한 유료 검증을 통과로 표시하지 않는다.

## 6. 최종 전달

한국어로 결과를 먼저 말하고 다음을 간결하게 남겨라.

- 원인별 변경 내용과 수정 파일.
- 각 완료 기준의 통과/실패/미검증 상태 및 재현 근거.
- 기존 분석 포인트, 병렬 실행, 캐시, 사용량과 취소 계약의 보존 여부.
- 실제 수행한 API 요청/비용 또는 추가 호출 0건이라는 사실.
- 남은 내용 오류와 적용 한계, 핵심 원리와 재검산 방법을 담은 짧은 학습 메모.

검증 보고서는 새 파일로 작성하고 기존 실험 기록을 보존한다. 테스트가 통과했다는 사실과 모든 논문의 과학적 정확성이 보장된다는 주장을 구분하라. 코드 주석은 간결한 영어, 사용자 설명은 한국어로 작성하며 사용자 설명에서 가운데점 문자를 사용하지 않는다.
