# 읽기 안내(Reading Guide) 설계 브리프

작성: 2026-09-05, `/impeccable shape` 인터뷰 결과. 구현 전 브리프이며 코드와 시각 방향 계약은 포함하지 않는다.

## 배경

2026-09-05 디자인 비평(21/40)에서 가장 큰 구조 문제로 "앱이 교차 검토를 지시하면서 5개 탭이 상호 배타적"이라는 점을 지적했다. 인터뷰에서 사용자는 핵심 과업을 다시 정의했다: **원문을 직관과 수식 양쪽으로 가장 빨리 이해하는 것**이 핵심이고, 논문 원문에는 건너뛴 자리(gap)가 많다. 가장 자주 막히는 gap은 직관 부재, 표기와 정의 미설명, 선행 지식 전제 세 가지다(수식 유도 건너뜀은 아님). 토큰 낭비를 우려하므로 자동 호출은 배제한다. 백엔드는 변경하지 않는다.

확인한 사실:
- 질문 도우미 API(`POST /analysis/{id}/chat`)는 `message`와 `history`만 받고 스트리밍으로 답하며 `tokens_in`, `tokens_out`, `cost_usd`를 돌려준다. 서버가 논문 전문 맥락을 붙인다.
- PDF 뷰어는 pdf.js 텍스트 레이어를 써서 드래그 선택이 가능하다.
- 주장, 그림, 표, 기호를 잇는 데이터는 없다. 근거 앵커는 레시피 파라미터에서 PDF 좌표로만 간다.
- 채팅 답변의 인용 칩(`citationFocus`, `[data-citation-anchor]`)이 그림/표 탭의 카드로 점프하는 라우팅이 이미 있다.

## 1. 과업과 대상

낯선 분야 논문을 읽는 대학원생과 연구자. 원문에서 막힌 자리(기호가 뭔지, 왜 이렇게 하는지, 전제된 배경이 뭔지)를 그 자리에서 풀고 다음 줄로 넘어가고 싶다. 오른쪽 패널의 모드는 Operate에서 **Read**(읽기 동반자)로 바뀌고, 왼쪽 PDF 뷰어는 그대로 Operate다.

## 2. 결과와 증거

성공은 원문 한 편을 끝까지 읽는 시간이 줄고, 막혔을 때 앱 밖(검색, 교과서)으로 나가는 횟수가 주는 것이다. 제품 고유 재료: 논문 전문을 아는 채팅 API, 연구자 프로필의 설명 수준, 페이지 점프와 본문 검색, 인용 칩 라우팅.

## 3. 선택한 방향: 한 번 만들고, 그다음은 토큰 0

### 읽기 안내 1회 생성
논문당 채팅 API를 한 번 호출해 고정 헤딩 3개짜리 마크다운을 받는다.
- **표기 사전**: 기호, 뜻, 첫 정의 페이지.
- **선행 지식**: 전제된 개념 3~6개, 각 2~3줄 primer와 이 논문에서 왜 필요한지.
- **섹션별 직관**: 섹션마다 무엇을 하려는지 한 단락.

생성 전에 예상 비용을 재분석 모달과 같은 문구 체계로 보여주고 확인을 받는다. 프롬프트에는 연구자 프로필의 설명 수준을 반영한다. 결과는 논문 id 기준으로 로컬에 저장해 다시 열어도 비용이 들지 않고, 재생성은 명시적 요청으로만 한다.

### 토큰 0 상호작용
- 표기 사전 항목 클릭: 기존 본문 검색으로 첫 정의 위치에 PDF 점프.
- 섹션 직관 항목 클릭: 해당 페이지로 점프.
- 요약 탭 본문의 "Fig. 3", "Table 2" 같은 문자열: 채팅과 같은 인용 칩으로 바꿔 그림/표 탭의 카드로 이동(기존 `citationFocus` 재사용).

### 선택 설명은 눌렀을 때만
PDF에서 드래그하면 선택 영역 위에 버튼 하나("이 부분 설명")가 뜬다. 누르면 "p.N의 다음 부분을 직관 먼저, 유도는 접어서 설명"이라는 고정 형식으로 질문 도우미에 보내고 답은 채팅 패널에 온다(채팅 1회 비용, 패널에 누적 비용 표시). 자동 호출은 없다. 답의 형식은 직관 한 단락과 접힌 유도.

### 초점 순간
기호 하나를 집었을 때 정의와 첫 등장 위치가 토큰 없이 즉시 뜨는 순간.

### 구현 결과
새 탭 "읽기 안내" 1개, PDF 뷰어의 선택 이벤트 노출, 채팅 패널에 외부 프롬프트 주입(기존 draft 상태 활용), 로컬 캐시 모듈, 프롬프트 템플릿 1개(프론트 strings), 요약 탭 인용 칩 파서 연결.

## 4. 범위와 경계

프로덕션 품질, 워크벤치만, 백엔드 변경 0.

안 하는 것(anti-goal):
- 스크롤을 따라 자동으로 바뀌는 섹션 안내(비용 때문에 유예).
- 유도 전체를 미리 생성.
- 오른쪽 패널 둘로 쪼개기(안내 탭과 인용 칩으로 교차 검토 수요가 대부분 해소되므로 유예).
- 백엔드 스키마와 분석 파이프라인 변경.

## 5. 상태와 범위

- 안내 미생성: 빈 상태에 예상 비용과 생성 버튼.
- 생성 중: 스트리밍 표시. 실패: 재시도.
- 캐시 있음: 즉시 표시, 생성 시각과 설명 수준 메타 한 줄.
- 재생성: 확인 모달(기존 결과 대체와 비용 명시).
- 프로필 설명 수준이 바뀐 뒤: 안내가 옛 수준으로 만들어졌다는 메타 표시, 재생성은 사용자 선택.
- 선택 텍스트 상한: 2,000자 초과 시 안내하고 전송하지 않음.
- 스캔 PDF(텍스트 레이어 없음): 선택 불가 안내.
- 현실적 규모: 기호 10~80개, 섹션 5~12개, 선행 개념 3~6개.

## 6. 상호작용과 배치

- 탭 구성은 5개 유지: 요약, 읽기 안내, 그림, 표, 레시피. **실험 계획은 레시피 탭 안의 하위 섹션으로 접는다**(사용자 결정).
- 표기 사전은 필터 입력 하나 있는 목록. 선행 지식은 카드. 섹션 직관은 아코디언.
- 선택 버튼은 PDF 위 팝오버 하나. 응답은 채팅 패널에서 본다.
- 기존 Quiet Minimal 어휘(칩 3종, 굵기 3단계, radius 토큰 6/12/pill)를 그대로 쓴다. 워크벤치 UI 계약(2026-08-04, 2026-08-05 스펙)을 따른다.

## 7. 제약과 열린 결정

- 캐시 저장소: IndexedDB 권장. `papers.notes`는 사용자 메모라 오염시키지 않는다.
- 안내 출력 형식: 마크다운 고정 헤딩 권장(JSON 파싱보다 견고, 기존 Markdown.tsx로 렌더). 접힌 유도를 위한 details 지원 여부는 구현 전 Markdown.tsx에서 확인한다.
- 비용 규모: 안내 생성 1회는 심층 분석 1단계와 비슷한 수준으로 추정(실측 아님). 생성 전 표시로 사용자가 판단한다.
- 표기 사전에서 첫 정의 위치 점프는 본문 검색의 첫 매치에 의존한다. 기호가 흔한 문자(t, x)이면 오매치가 나므로, 안내에 페이지 번호를 함께 받아 그 페이지부터 검색한다.
- 요약 탭 인용 칩 파서는 채팅의 `CitationTarget` 파서를 재사용하되, 요약 본문은 마크다운 문자열이므로 렌더 단계에서 치환한다.
