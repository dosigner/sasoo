# Sasoo 1.0.1 상세 요약과 읽기 GUI 최종 명세

작성일: 2026-09-22

상태: 기능 구현, 자동 검사와 개발 앱 GUI의 독립 검토를 완료했다. 실제 모델 검증은 3개 캠페인까지 실행했으나 일부 원문 대조 기준이 미충족이다. 스크롤/보충 참조/기존 PDF decoder 문제의 보완과 최종 178장 GUI 검증은 통과했다. 실행 여부와 통과 근거는 [검증 기록](../../validation/2026-09-22-v1.0.1-summary-reading.md)을 따른다. 과학적 정확성 전체, 패키지 또는 사용자 학습 효과 검증의 완료로 표현하지 않는다.

구현 순서와 검증 명령은 [구현 계획](../plans/2026-09-22-v1.0.1-summary-and-reading.md)에 기록한다. 이 명세가 콘텐츠와 GUI의 기준이다.

## 1. 목표와 범위

사용자가 요약을 읽고 논문의 문제, 방법의 작동 원리, 주요 결과, 한계를 자기 말로 설명할 수 있어야 한다. 읽기 안내의 섹션별 직관에서 기대하게 된 질문의 답을 요약에서 바로 읽을 수 있어야 한다. 바이오와 로보틱스에서는 다른 환경으로 옮겨 쓸 때 확인할 조건까지 설명한다.

| 요구사항 | 완료를 관찰하는 방법 |
|---|---|
| R1. 이해 중심 상세 요약 | 문제, 왜 방법이 통하는지, 결과가 성립한 조건, 해석의 한계를 원문 근거와 함께 찾는다. |
| R2. 섹션별 핵심 답변 | 각 항목의 질문과 짧은 답이 추가 클릭 없이 보이며, 필요한 설명과 근거를 펼쳐 읽는다. |
| R3. 적용 전 확인 조건 | 원문의 조건, 그 조건의 근거 성격, 옮겨 쓰기 전 확인할 점을 구별한다. |
| R4. 분야에 맞는 설명 | 바이오는 실험 모델과 측정의 의미, 로보틱스는 관측과 제어 및 실물 검증 범위를 설명한다. |
| R5. 읽기 GUI | 제목, 본문, 강조, 학명, 수식, 인용, 코드가 각 역할에 맞게 보인다. |
| R6. 비용과 기존 데이터 보존 | 조회와 탭 이동은 새 생성 요청을 보내지 않는다. 구형 결과도 계속 읽는다. |
| R7. 화면과 내보내기 일치 | 화면의 새 답변과 적용 조건이 기존 Markdown/HTML 내보내기에서도 누락되지 않는다. |
| R8. 정직한 상태 표시 | 미생성, 진행, 실패, 구형 결과, 근거 부족을 완료나 적용 가능으로 오인하지 않는다. |

이번 범위에 포함하지 않는 것: 사용자의 실험실이나 로봇 설정 수집, 개인 환경과의 자동 비교, 새 실험 프로토콜과 코드의 자동 실행, 임상 적용 판단, 실물 장비 제어, 실험 탭 구현, 외부 문헌 자동 검색, 종합 뷰 개편, 새 전역 디자인 시스템과 설정 화면.

## 2. 기존 결정과 이번 변경의 경계

- [DEC-017](../../product-decisions.md#dec-017--deep_dive-스키마-분해-detailed_analysis를-구조화-필드로)의 여섯 필드 `problem_definition`, `as_is`, `to_be`, `solution`, `method_summary`, `key_results`를 유지한다. 필드가 빈약하면 분량 지시를 조정할 수 있다는 재검토 조건에 해당한다.
- `as_is`와 `to_be`는 해당 구도가 없으면 비운다. 리뷰와 이론 논문에 공학식 문제 해결 구도를 강요하지 않는다.
- `detailed_analysis` 단일 장문 필드를 새 생성 스키마에 되살리지 않는다. 기존 저장 결과의 표시용 폴백은 유지한다.
- `comparison_scope = in_paper_only`와 심층 분석 출력 상한 16,000 tokens를 유지한다. 상한을 올려 분량 문제를 숨기지 않는다.
- 필드 설명을 프롬프트에 명시하고 새 생성에서 필수 키가 누락되지 않게 한다. 형식상 필수인 배열도 근거가 없으면 빈 배열을 허용한다.
- [읽기 안내 설계](2026-09-05-reading-guide-design.md)의 원문 순서, 기존 세 헤딩, 명시적 생성과 재생성, 캐시 재사용을 유지한다. 당시 ‘백엔드 변경 0’은 읽기 안내 도입 범위의 제약이다. 이번 상세 요약은 기존 심층 분석 출력을 확장하므로 백엔드 변경을 포함한다.
- 기존 읽기 안내의 ‘5~12개’ 지시는 그대로 두고, 새 핵심 답변은 실제 절 수보다 항목을 부풀리지 않는다. 12개를 넘는 논문은 핵심 절을 원문 순서로 선별한다.
- [Quiet Minimal 계약](2026-08-04-workbench-right-panel-design.md)의 Pretendard, 굵기 400/500/650, 기존 전경색과 surface, radius 6/12/pill을 사용한다. 2026-07-12 명세와 굵기 규칙이 다르면 더 최근인 2026-08-04 계약을 따른다.
- 탭은 현재 코드의 요약, 종합, 읽기 안내, 그림, 표, 레시피를 유지한다. 초기 브리프의 과거 탭 개수로 되돌리지 않는다.

## 3. 용어와 콘텐츠 계약

**섹션별 핵심 답변:** 논문의 실제 절이 다루는 질문에 대한 짧은 답과 설명. 읽기 안내의 직관과 대응하지만, 근거가 여러 절에 걸치면 여러 출처를 함께 가진다.

**옮겨 쓸 때 확인할 조건:** 원문 방법을 다른 연구나 구현 환경에 적용하기 전에 비교해야 할 조건. 사용자의 환경에서 적용 가능하다는 판정을 뜻하지 않는다.

### 3.1 전체 요약의 깊이

| 기존 필드 | 1.0.1 생성 기준 |
|---|---|
| `problem_definition` | 2~4문장. 문제가 생기는 상황, 기존에 막히는 지점, 해결의 의미. |
| `as_is`, `to_be` | 각각 2~3문장, 1~2문장. 해당 구도가 있을 때만 작성. |
| `solution` | 3~5문장. 핵심 아이디어와 작동 이유를 인과 순서로 설명. |
| `method_summary` | 2~3문단, 문단당 2~4문장. 입력/실험 대상, 핵심 처리, 관측 또는 출력. |
| `key_results` | 1~2문단. 비교 대상, 조건, 수치와 단위, 불확실성이 보고되면 함께 설명. |
| `weaknesses` | 핵심 해석 한계를 우선. 각 항목에 원문 위치와 저자 설명인지 Sasoo의 해석인지 드러나게 작성. |

이는 생성 분량 목표다. 글을 채우기 위해 사실을 추가하거나 UI에서 수치와 한계를 잘라내지 않는다. 기존 연구자 설명 수준은 어휘와 배경 설명의 깊이에 적용하고, 근거와 적용 조건을 빼는 이유로 사용하지 않는다.

### 3.2 새 출력 필드

기존 `deep_dive` JSON에 두 배열만 추가한다. API 엔드포인트와 DB 테이블은 추가하지 않는다.

```ts
interface SectionAnswer {
  section_title: string;
  question: string;
  answer: string;
  explanation: string;
  source_refs: string[];
}

interface TransferCheck {
  item: string;
  paper_condition: string;
  condition_basis: 'reported' | 'inferred' | 'not_reported';
  check_before_transfer: string;
  source_refs: string[];
}
```

`section_answers`는 최대 12개다. 각 항목은 원문 절 제목과 순서를 유지한다. `question`은 그 절에서 풀어야 하는 질문 한 문장, `answer`는 질문에 직접 답하는 1~2문장, `explanation`은 작동 이유와 증거를 푸는 2~4문장이다. 별도 설명이 필요하지 않으면 `explanation`은 빈 문자열이다. 전역 요약과 같은 문장을 반복하지 않고 해당 절의 논리와 증거를 보충한다.

`transfer_checks`는 최대 8개다. 각 항목의 `paper_condition`은 원문 조건 1~2문장, `check_before_transfer`는 왜 확인해야 하는지 포함한 1~2문장이다. 후자는 항상 적용을 위한 확인 제안이며 원문에서 실험한 사실로 표시하지 않는다.

| `condition_basis` | 표시 | 작성 기준 |
|---|---|---|
| `reported` | 원문에 명시 | 제공된 논문 자료에서 확인한 조건. 출처가 반드시 있어야 한다. |
| `inferred` | 원문에서 추론 | 원문에 있는 정보로 도출한 조건. 도출 이유와 입력 정보의 출처를 설명한다. |
| `not_reported` | 제공 자료에서 확인 못함 | 중요한데 확인하지 못한 조건. 보충자료를 받지 않았다면 논문 전체에 없다고 단정하지 않는다. |

`source_refs`는 항목당 최대 4개의 원문 절 제목, 그림 번호 또는 표 번호다. 핵심 답변과 `reported`/`inferred` 조건에는 최소 1개의 출처가 필요하다. 새 필드에는 페이지 번호를 생성하지 않는다. 현재 읽기 안내의 인쇄 페이지와 레시피의 PDF 파일 페이지가 다르므로, 이번에 새 페이지 연결을 만들면서 두 기준을 섞지 않는다. 기존 페이지 이동의 의미는 바꾸지 않는다.

근거 성격은 검증 인증이나 신뢰도 점수가 아니다. 초록색 완료 표시나 ‘적용 가능’ 표시를 붙이지 않는다. 기존 원문 인용 칩을 재사용하되 실제 보유한 그림/표만 이동 가능하게 한다. 새 `source_refs`는 단일 그림/표 참조 전체가 일치할 때만 연결한다. `Figure 1—figure supplement 1`처럼 미제공 보충 자료를 가리키는 문자열을 본문 `Figure 1`로 연결하지 않는다. 존재하는 그림이라는 사실만으로 그 주장의 근거가 검증됐다고 표시하지 않는다.

두 배열은 새로운 생성 응답에서 필수 키이며, 입력 자료가 부족하면 빈 배열을 허용한다. 두 필드가 모두 없는 성공한 저장 결과는 구형 결과다. `_parse_error` 또는 `error`가 있는 실패 응답은 구형으로 표시하지 않는다. 한 필드만 있거나 타입과 항목 구성이 잘못된 새 응답은 형식 오류이며 완료로 표시하지 않는다. 생성 전에 문서 내용의 존재를 추측해 빈 항목을 채우지 않는다. 스크리닝으로 건너뛴 단계는 저장된 안내 문구를 보존한다.

### 3.3 분야별 확인 관점

분야는 연구자 프로필만으로 판정하지 않는다. 논문에 실제 등장하는 실험과 방법을 기준으로 아래 지침을 적용한다. 바이오와 로보틱스가 섞인 연구에는 두 관점을 필요한 항목에만 적용한다.

| 관점 | 바이오 | 로보틱스 |
|---|---|---|
| 대상 | 세포주, 개체 또는 검체, 연구 유형과 특성 | 로봇 구조와 자유도, 작업, 센서와 구동기 |
| 입력과 조작 | 처치와 대조 조건, 측정 시점, 분석 입력 | 관측 입력, 행동 출력, 토크/속도/목표 위치 등의 제어 인터페이스 |
| 성립 조건 | 배양/처리/측정/정규화 중 핵심 결과에 영향을 주는 조건 | 좌표계, 단위, 주기, 지연, 보정, 환경 및 동역학 조건 |
| 결과 해석 | 독립 표본과 반복 측정, 효과 크기와 불확실성, 상관과 인과 | 성공 정의, 초기 조건, 반복 횟수, 실패 사례, 비교 방법 |
| 옮길 때 확인 | 모델, 시약, 장비, 분석법 차이가 결론에 미치는 영향 | 하드웨어와 계산 자원 차이, 시뮬레이션과 실물 검증의 경계 |

바이오의 기존 `cell.md`에서 `n < 3`을 일괄적으로 무의미하다고 판정하는 지침을 수정한다. 독립 표본의 정의와 실험 설계, 효과 크기 및 불확실성을 함께 평가한다. 특정 실험 기법에 관한 검토 항목을 모든 바이오 논문에 강제하지 않는다.

로보틱스는 현재 screening의 분야 enum에 별도 값이 없으므로 새 분류기나 에이전트를 만들지 않는다. 공통 심층 분석 지시문에 논문 내용에 따른 로보틱스 확인 관점을 넣는다. 원문에 없는 주기, 질량, 마찰, 시약 농도 등을 기본값으로 보충하지 않는다.

임상 논문에는 실험실 프로토콜 체크리스트를 강요하지 않고 연구 대상, 측정 지표, 연구 설계와 일반화 범위를 설명한다. 이론과 리뷰에는 가정, 문헌 선정 범위, 적용 가능한 문제 조건으로 전환한다.

## 4. GUI 개선안

### 4.1 화면 골격과 읽는 순서

기존 PDF와 오른쪽 패널 분할을 유지한다. 새 탭이나 별도 설정을 만들지 않는다. 상태부, 재분석 확인, 기존 패널 폭 조절을 재사용한다.

```text
┌───────────────────────────┬────────────────────────────────────────┐
│                           │ 분석 상태와 기존 조작                  │
│                           │ 요약 | 종합 | 읽기 안내 | 그림 | …     │
│                           ├────────────────────────────────────────┤
│                           │ 스크리닝                               │
│          원문 PDF         │ 짧은 전체 요약과 기존 메타             │
│                           │                                        │
│                           │ 심층 분석                         [접기]│
│                           │ 핵심 내용 / 섹션별 답변 / 적용 조건    │
│                           │                                        │
│                           │ 문제와 해결 원리                       │
│                           │ 기존 구조의 제목과 설명                │
│                           │ 방법 / 결과 / 해석의 한계              │
│                           │                                        │
│                           │ 섹션별 핵심 답변                       │
│                           │ 원문 절 제목                           │
│                           │ 왜 이 방법을 선택했나요?               │
│                           │ 질문에 대한 짧은 답이 항상 보임        │
│                           │ [근거와 설명 펼치기]                   │
│                           │                                        │
│                           │ 옮겨 쓸 때 확인할 조건                 │

│                           │ 원문 근거                     [Fig. 2] │
│                           │                                        │
│                           │ [추가 평가 펼치기]                     │
│                           │ [인용 분석 펼치기]                     │
└───────────────────────────┴────────────────────────────────────────┘
```

위 도식은 구조 설명용이며 내용은 실논문의 분석 결과가 아니다. 기존 여섯 필드의 의미와 순서는 그대로다. `weaknesses`를 ‘해석의 한계’로 읽는 흐름에 배치하고, 핵심 답변과 적용 조건 다음에 추가 평가를 둔다. `novelty_assessment`, `comparison_to_prior_work`, `strengths`, `suggested_improvements`, `practical_applications`, `follow_up_questions`는 추가 평가에서 계속 접근 가능하다. `comparison_scope` 설명은 해당 비교 평가와 함께 표시한다.

스크리닝과 심층 분석은 기본으로 펼친다. 인용 분석은 심층 분석 아래로 옮기고 기본으로 접는다. 분석 단계 실행 순서는 변경하지 않는다. 사용자가 펼침 상태를 바꿨다면 같은 논문에서 탭을 이동해도 그 상태를 유지하고, 다른 논문을 열면 기본값으로 돌아간다.

세 개의 목차 링크는 심층 분석 본문 안의 위치로 이동하는 링크다. 추가 탭과 고정 헤더가 아니다. 좁은 폭에서는 줄바꿈한다. 같은 제목이 다른 Phase에 있어도 해당 심층 분석 안에서만 이동한다.

### 4.2 핵심 답변과 읽기 안내의 연결

- 모든 핵심 답변의 원문 절 제목, 질문, 짧은 답은 기본 노출한다. 설명과 출처만 `<details>`로 펼친다. 한 항목을 펼쳐도 다른 항목을 강제로 닫지 않는다.
- 읽기 안내의 기존 섹션별 직관에는 해당 답변이 있을 때 ‘요약의 답변 보기’ 링크를 붙인다. 새 LLM 호출 없이 심층 분석 결과를 참조한다.
- 제목 비교는 Unicode NFC, 연속 공백 정리, 대소문자 통일 뒤 정확히 일치하는 경우만 허용한다. 절 번호와 문장부호를 지우거나 순서와 유사도로 추측하지 않는다. 중복 제목이면 특정 답변으로 연결하지 않는다.
- 일치하지 않거나 구형 분석이면 ‘요약 전체 보기’만 제공한다. 자동으로 답변을 만들거나 다른 절로 보내지 않는다.
- 연결 시 요약 탭과 심층 분석을 펼치고, 해당 답변 제목으로 스크롤 및 포커스를 옮긴다. 답의 전문은 이미 보이므로 설명을 자동으로 펼칠 필요는 없다.
- 그림이나 표를 보고 요약으로 돌아오면 현재 논문 안에서 이전 요약 스크롤 위치를 복원한다. 명시적인 답변 이동은 그 위치를 우선한다. DB에 읽기 위치를 저장하지 않는다.
- 실제 창 검사에서 `scrollIntoView`가 바깥 `overflow: hidden` 조상까지 이동시키는 문제가 확인됐다. 읽기 목차와 답변 이동은 공유 함수로 읽기 패널에만 상대 좌표 `scrollTo`를 적용하고, 포커스는 `preventScroll`로 옮긴다.

### 4.3 타이포그래피와 글의 역할

요약과 읽기 안내에만 `reading-prose` 범위를 적용한다. 전역 `text-sm` 값을 바꾸지 않는다. 채팅, 설정, 라이브러리, 종합 뷰의 글 크기를 함께 변경하지 않는다.

| 역할 | 구현 기본값 | 토큰과 규칙 |
|---|---|---|
| 주요 제목 | 17px / 26px / 650 | 기존 `text-lg`; 의미 있는 HTML heading 사용 |
| 질문과 하위 제목 | 15px / 24px / 650 | 기존 `text-base`; 질문은 완결된 문장 |
| 본문과 적용 조건 | 15px / 26px / 400 | 기존 `text-base`, 본문 전경색 |
| 보조 설명과 출처 | 13px / 20px / 400 또는 500 | 기존 `text-sm`, 보조 전경색; 핵심 조건을 여기에 숨기지 않음 |
| 인라인 코드 | 13px / 본문 행간 | 기존 mono font, 약한 surface 배경 |
| 코드 블록 | 13px / 20px | 기존 mono font, radius 12, 내부 가로 스크롤 |

위 px 값은 root 16px에서의 값이며 rem으로 구현한다. 새 행간 값은 문서 전용 CSS 변수 `--reading-leading-body: 1.625rem`, `--reading-leading-heading: 1.625rem`, `--reading-leading-subheading: 1.5rem`으로 정의한다. 본문 최대 폭은 문서 전용 `--reading-max-width: 44rem`이다. 넓은 패널에서도 왼쪽 정렬을 유지한다.

본문 문단 간격 12px, 주요 제목 앞 24px/뒤 8px, 문서 묶음 사이 24px를 기존 spacing 단위로 적용한다. 본문은 한국어 단어 단위 줄바꿈을 우선하고, 긴 URL이나 식별자는 넘칠 때만 분리한다. 목록은 `list-outside`로 여러 줄 들여쓰기를 맞춘다.

| Before | After | Why |
|---|---|---|
| 분석 본문 13px, 행간 28px, 보조색 | 본문 15px, 행간 26px, 본문색 | 글자 크기와 줄 사이 거리를 함께 조정 |
| 굵은 라벨이 제목과 본문 강조를 겸함 | 실제 heading과 본문 `strong`을 구분 | 문서 구조, 목차, 스크린리더 탐색을 일치시킴 |
| 분석 `strong`의 굵기가 브라우저 기본에 의존 | 650과 본문색으로 명시 | 기존 굵기 계약 안에서 일관되게 강조 |
| 한글 인용문 전체를 기울임 처리 | 인용은 정체와 얇은 왼쪽 선, 출처로 표현 | 긴 한글 문장의 읽기 흐름 유지 |
| 코드에 단일 색만 적용, 복사 동작 없음 | 언어 표시, 제한된 구문 강조, 복사 버튼 | 코드와 설명을 구별하고 그대로 복사 가능 |

`strong`은 짧은 핵심 결론과 중요한 조건에 사용한다. 문단 전체를 굵게 만들지 않으며, 굵기만으로 사실과 추론을 구별하지 않는다. `em`은 원문 의미를 보존한다. 학명처럼 필요한 이탤릭을 제거하지 않고, 한글 문단을 장식 목적으로 전부 기울이지 않는다. 유전자명과 단백질명의 표기 관례를 일괄 치환하지 않는다.

수식은 기존 KaTeX를 사용하고 코드 상자로 바꾸지 않는다. 값과 단위는 일반 본문으로 유지한다. 넓은 수식과 표는 해당 요소 안에서만 가로 스크롤되게 한다.

좁은 패널의 실제 검사에서 한글 표 셀이 지나치게 좁아지는 문제를 확인하여 읽기 표 셀의 최소 폭을 8rem으로 두었다. 표 전체를 패널 안에서 스크롤하며 본문 글자 크기는 줄이지 않는다.

### 4.4 코드 표시와 상호작용

- 코드 블록 위에 언어명과 ‘코드 복사’ 버튼을 둔다. 언어를 모르면 ‘코드’로 표시하고 자동 추정하지 않는다.
- 설치돼 있는 `rehype-highlight`를 재사용한다. 구문 색은 기존 `fg`, `fg-secondary`, `accent`만 사용하고 새로운 색상표를 도입하지 않는다. 알 수 없는 언어는 평문 폴백이다.
- 복사는 실제 `<code>`의 `textContent`를 사용해 여러 줄과 들여쓰기를 보존한다. 성공 시 ‘복사했어요’를 1.5초 표시하고, 실패 시 ‘복사하지 못했어요’를 표시한다. 실패를 성공으로 처리하지 않는다.
- 인라인 코드에는 복사 도구를 붙이지 않는다. 코드나 링크 안의 `Fig. 3`을 인용 칩으로 바꾸지 않는다.
- 코드 실행 버튼과 새 코드 생성은 제공하지 않는다. 원문 코드와 설명용 의사코드는 주변 설명에서 구분한다.
- 제목과 인용, 접기, 복사 버튼은 키보드 포커스가 보이고 접근 가능한 이름을 가진다. 새 조작의 클릭 영역은 최소 32px, 거듭 접하는 문서 링크에는 확대/축소 모션을 넣지 않는다.
- 색 전환은 기존 150ms 토큰을 사용한다. 읽기 본문과 탭 재진입의 `fade-in-up`을 제거하고, 본문 높이와 글자 크기를 애니메이션하지 않는다. 키보드 이동과 reduced motion에서는 위치 이동 애니메이션 없이 반응한다.

### 4.5 상태와 작은 패널

| 상태 | 화면 동작 |
|---|---|
| 분석 전 또는 진행 중 | 기존 상태와 실제 확보된 결과만 표시. 빈 새 항목을 완료된 것처럼 채우지 않음. |
| 새 형식의 정상 결과 | 핵심 답변과 적용 조건 표시. 빈 배열이면 ‘이번 분석에서 작성된 항목이 없어요’ 표시. |
| 1.0.0 결과 | 기존 본문 표시. ‘이전에 생성한 분석이에요. 재분석하면 핵심 답변과 적용 전 확인 조건을 함께 만들어요.’ 표시. 기존 재분석 진입점 사용. |
| 새 형식 오류 | 기존 단계 실패 표시와 재시도 동작 사용. 기본값으로 메워 완료하지 않음. |
| 분석 건너뜀 | 기존 저장 `message`를 보존하고 단계와 진행 목록에 중립적인 ‘건너뜀’을 표시. 성공 체크나 구형 재생성 안내로 표시하지 않음. |
| 읽기 안내 미생성 | 기존 생성 확인과 비용 안내 유지. 요약만 보려고 안내를 생성하지 않음. |
| 제목 불일치 또는 중복 | 요약 전체 이동만 제공. 관련성이 확인되지 않은 개별 링크를 생성하지 않음. |
| 근거를 확인하지 못함 | 자료 범위를 명시하고 출처를 추측하지 않음. |

앱 창은 현재 기본 1400×900, 최소 1024×680이다. 두 크기와 1280×800, 1600×1000에서 PDF/요약 1:1과 기존 1:2, 2:1 프리셋을 확인한다. 오른쪽 패널은 별도로 320px, 375px, 560px, 768px 폭에서 검증한다. 최소 지원 창보다 작은 뷰포트를 앱의 새 지원 규격으로 선언하지 않는다.

패널 padding은 기본 20px, 패널 폭 400px 미만에서는 16px이다. container query로 패널 폭을 기준으로 적용한다. 320px 미만에서도 본문을 축소하지 않고 컨트롤이 줄바꿈한다. 새 적용 조건은 여러 열 표가 아닌 세로 목록이다. 긴 코드와 표를 제외하고 패널 전체의 가로 스크롤이 생기지 않아야 한다.

## 5. 생성과 캐시

새 답변과 확인 조건은 기존 심층 분석 한 번에서 생성한다. 읽기 안내의 생성 경로와 캐시는 변경하지 않는다. 두 화면은 같은 `deep_dive` 결과를 참조한다.

기존 프롬프트 기반 캐시 키에 새 지시문 변경이 반영되므로, 사용자가 재분석할 때 새 결과를 만든다. 업그레이드와 조회만으로 재분석하지 않고 구형 결과를 지우지 않는다. 원래 분석된 파라미터와 근거를 다시 LLM의 사실 출처로 취급하지 않고 PDF 또는 제공 텍스트를 확인하게 한다.

기존 `_run_deep_dive`의 검사는 JSON 구문 중심이었다. 새 두 필드는 별도 구조 검사를 거쳐 키, 타입, 최대 항목 수, 근거 enum을 검증한다. 생성 경로는 필수 필드 누락을 오류로 처리하며 기존 비용과 사용량을 기록한다. 구형 저장 결과 읽기와 새 생성 검증은 구분하고, `_parse_error`/`error` 응답을 구형 성공 결과로 해석하지 않는다.

추가 자동 보정 호출과 재시도를 만들지 않는다. 출력 상한에 걸린 응답을 성공으로 취급하지 않는다. 실패 후 이전 결과 표시와 재분석 상태는 기존 데이터 보존 계약에 따라 확인한다.

실제 모델 검증 보완: 중복 JSON 키와 비표시 제어문자는 원응답/비용을 보존한 오류로 기록한다. OpenAI 심층 분석 요청의 스키마 복사본만 strict 호환으로 제한한다. 요청에는 모든 키를 요구하되 as_is/to_be는 빈 문자열을 허용하며 공유 schema와 저장 타입은 유지한다. 기존 critic persona/체크리스트는 이해 중심 심층 분석의 system에서 제외하고, 다른 단계의 persona와 독자 프로필/설명 수준은 보존한다. 실제 문헌에 해당하는 분야별 방법 설명은 공통 심층 지침을 따른다.

실제 코드 보완: 저장된 시각화가 없을 때 결과 조회 훅이 생성형 legacy Mermaid API를 자동 호출하던 폴백을 제거했다. 보고서 API에는 다운로드 GUI가 없어 요약 하단에 Markdown/HTML 형식 선택과 명시적 내보내기 버튼을 추가했다. HTML도 기존 Markdown 렌더러를 사용하고 MathML로 수식을 읽게 한다. 두 변경 모두 새 분석 요청을 만들지 않는다.

## 6. 완료 기준과 검증 입력

자동 검증은 새 JSON 구조, 구형 결과, 잘못된 응답, 정확한 제목 연결, GUI 상태, 내보내기 누락을 대상으로 한다. 문장의 과학적 정확성은 자동 스키마 검사로 보장됐다고 주장하지 않는다.

실논문 검증은 바이오 2편(실험 연구, 분석 방법), 로보틱스 2편(제어, 학습 기반 조작), 이론 1편, 리뷰 1편으로 한다. 각 논문에서 다음 여섯 기준 질문과 원문 위치를 먼저 사람이 기록하고 출력을 대조한다: 문제, 작동 이유, 결과와 조건, 주요 한계, 중요한 적용 전 확인 조건, 확인되지 않은 정보. 논문 제목, DOI/URL, PDF 해시, 사용한 본문/보충자료 범위를 검증 기록에 남긴다.

통과 기준은 여섯 편에서 핵심 결론을 뒤집는 오류, 지어낸 수치와 조건, 사실과 제안의 혼동, 잘못된 근거 이동이 0건인 것이다. 기본 화면에서 질문과 짧은 답을 모두 읽을 수 있어야 한다. 이해 목표 B는 결과물 검토와 설명 과제로 평가하며, 실제 사용자 학습 효과를 검증한 수치로 표현하지 않는다.

실제 앱에서 밝은/어두운 테마, 100%/200% 확대, 키보드와 reduced motion, 코드 복사 성공/실패, 긴 수식과 표, 재분석 취소 및 구형 결과를 확인한다. 일반 본문 대비 4.5:1 이상, 큰 글자와 조작 요소 경계 3:1 이상을 확인한다. 최소 한 개의 표시 수치와 단위, 한 개의 근거 위치, 한 개의 누락 조건을 원문과 대조한다.

기존과 개선 프롬프트의 입력/출력 tokens, 비용, 생성 시간을 같은 논문과 모델 설정에서 기록한다. 단계당 호출을 추가하지 않으며 16,000 tokens 상한을 유지한다. 비용과 시간 증가분은 공개하고, 반복 설명이 원인이면 분량과 프롬프트를 조정한다.

## 7. 판단의 근거

- [Nature Reporting Summary](https://www.nature.com/documents/nr-reporting-summary-flat.pdf): 독립 표본과 반복 측정, 효과 크기, 불확실성과 실험 설계의 보고 항목.
- [ROS REP-103 공식 원문](https://raw.githubusercontent.com/ros-infrastructure/rep/master/rep-0103.rst): 단위와 좌표 관례의 불일치가 통합 오류를 만든다는 근거.
- [Setting up a Reinforcement Learning Task with a Real-World Robot](https://arxiv.org/abs/1803.07067): 실물 로봇의 작업 설정과 재현성의 관계.

위 자료는 설계 관점의 근거다. 특정 사용자의 논문을 분석할 때 자동으로 비교 문헌으로 삽입하지 않는다. UI 값과 기본 펼침 상태는 기존 코드 및 디자인 계약을 바탕으로 선택한 설계값이며, Emil의 스킬이 규정한 고정 수치로 주장하지 않는다.
