# 설정 페이지 리디자인 설계

- 작성일: 2026-08-01
- 상태: 검토 대기
- 선행: `2026-07-31-ai-provider-selection-design.md` (AI 공급사 선택)
- 대상: `frontend/src/pages/Settings.tsx` (724줄), `frontend/src/index.css`

## 왜 지금인가

AI 공급사 선택 기능이 이 페이지의 정보구조를 무너뜨린다. 현재 배치는 이렇다.

| 섹션 | 실제 내용 |
|---|---|
| 모델 키 | Gemini 키 **하나만** |
| 이미지 생성 | **OpenAI 키** + 도해 생성 모델 + 도해 품질 |

OpenAI 키가 "이미지 생성" 섹션에 있다. gpt-image-2를 쓰던 시절에는 말이 됐지만, 이제
그 키는 논문 분석 전체를 좌우한다. 공급사 선택을 추가하면 "모델 키" 섹션에 키가 하나,
"이미지 생성" 섹션에 키가 하나 남아 사용자가 두 곳을 오가야 한다.

기능을 얹기 전에 구조를 고치는 편이 싸다.

## 현재 상태 진단

코드를 읽어 확인한 문제 6건이다. 시각 검증은 하지 못했다(Chrome 확장 미연결) —
아래는 전부 코드 근거다.

**1. 저장 버튼이 스크롤 밖으로 사라진다** (사용자 지적 사항)

페이지 높이는 대략 1,400~1,700px인데 뷰포트는 보통 800~900px다. 저장 버튼은
헤더 카드 안에 있어(`Settings.tsx:398`) 아래쪽 항목을 편집하는 동안 화면 밖이다.
보관함 경로나 테마를 바꾸고 나면 저장하러 맨 위로 올라가야 한다.

**2. 저장 버튼이 2개인데 둘 다 전체 저장이다**

헤더(`:398`)와 보관함 경로 행 안(`:624`)에 하나씩 있고 **둘 다 같은 `handleSave`**를
호출한다. 경로 옆에 붙은 버튼은 "이 항목만 저장"처럼 보이지만 실제로는 API 키까지
전부 PATCH한다. 위치가 거짓말을 하고 있다.

**3. 선택지가 하나뿐인 select가 2개 있다**

- `pdf_parser_mode` — 옵션 `java` 하나
- `extraction_pipeline_version` — 옵션 `resolver_v1` 하나

고를 수 없는 선택 컨트롤이다. 사용자에게는 "뭔가 정해야 하나?"라는 부담만 준다.

**4. 공급사 선택 추가로 select 2개가 파생값이 된다**

선행 스펙의 통짜 전환 결정에 따라 `image_provider`와 `pdf_visual_engine`은
`ai_provider`의 미러가 된다. 사용자가 직접 만질 값이 아니므로 UI에서 사라져야 한다.

**5. 테마만 동작 모델이 다르다**

테마는 즉시 적용되고 localStorage에도 바로 쓰이는데(`:214-223`) 서버 저장은
`handleSave`를 눌러야 한다. 다른 항목은 전부 저장 후 반영이다. 같은 페이지에서
두 가지 규칙이 섞여 있다.

**6. `.settings-savebar`가 정의만 되고 아무도 안 쓴다**

`index.css:305-307`에 `border-t border-border/80 bg-surface/95`로 정의돼 있으나
`Settings.tsx` 어디서도 참조하지 않는다. 하단 고정 저장바를 만들려다 만 흔적으로
보인다. 이번 작업이 그 자리를 채운다.

## 설계

### 방향

새 비주얼 언어를 만들지 않는다. 이 앱에는 이미 라이트/다크 페어 토큰, 보라 액센트
(`124 90 232`), `--radius-surface: 12px` / `--radius-control: 6px`, 커스텀 이징
(`--ease-out-strong`)이 갖춰져 있다. 여기서 할 일은 **정보구조 교정과 저장 인터랙션
수정**이다. 장식을 더하지 않는다.

### A. 새 정보구조

결정 기준 하나: **사용자가 이 값을 직접 정하는가.** 아니면 화면에서 뺀다.

| # | 섹션 | 항목 | 비고 |
|---|---|---|---|
| 1 | **AI 공급사** | 공급사 선택 (OpenAI / Google) | 신규 — 이 페이지의 최상위 결정 |
| | | OpenAI API 키 | "이미지 생성"에서 이동 |
| | | Google Gemini API 키 | "모델 키"에서 이동 |
| 2 | **분석** | 그림 판독 방식 (AI 판독 / 빠른 추출) | 유지 + 라벨 개선 |
| | | 도해 품질 (high/medium/low) | 유지 |
| | | 업로드 후 자동 분석 | 유지 |
| 3 | **보관함** | 논문 저장 경로 | 유지, 인라인 저장 버튼 제거 |
| 4 | **화면** | 테마 | 유지 |
| 5 | **사용량과 비용** | CostDashboard | 유지 |

**제거되는 컨트롤 3개**

| 컨트롤 | 사유 |
|---|---|
| 도해 생성 모델 (`image_provider`) | `ai_provider`의 파생값 |
| PDF 파서 엔진 (`pdf_parser_mode`) | 선택지 1개 |
| Figure/Table 추출 경로 (`extraction_pipeline_version`) | 선택지 1개 |

설정 키 자체는 DB에 남는다. **UI에서만 사라진다.** 뒤 둘은 나중에 선택지가 늘면
다시 노출하면 된다.

컨트롤 10개 → 8개.

#### 교정: `pdf_visual_engine`은 파생값이 아니다

이 문서의 초안은 `pdf_visual_engine`을 `image_provider`와 함께 `ai_provider`의
미러로 분류했다. **틀렸다.** 코드를 확인한 결과:

- 값 도메인이 `{gemini, odl}`이다 — `{openai, gemini}`가 아니다
- `api/settings.py:344`가 그 둘 외의 값을 400으로 거부한다. `openai`를 미러링하면
  저장이 실패한다
- `main.py:138`에서 `SASOO_PDF_VISUAL_ENGINE` 환경변수로 심겨 `odl_parser`가 읽는다

즉 이건 공급사 선택이 아니라 **"LLM 비전으로 판독할까, 로컬 Java 파서로 빠르게
뽑을까"** 라는 독립된 선택이다. `gemini`는 공급사 이름이 아니라 "LLM 비전 경로"를
가리키는 레거시 이름이다.

따라서 **미러링 대상은 `image_provider` 하나뿐이고**, `pdf_visual_engine`은 UI에
남긴다. 다만 "Figure 추출 엔진 / gemini·odl"이라는 현재 표기로는 사용자가 무엇을
고르는지 알 수 없으므로 라벨을 바꾼다.

| | 현재 | 변경 |
|---|---|---|
| 라벨 | Figure 추출 엔진 | 그림 판독 방식 |
| 옵션 `gemini` | `gemini` | AI 판독 (정확) |
| 옵션 `odl` | `odl` | 빠른 추출 (로컬) |

저장되는 값은 그대로 `gemini` / `odl`이다. 백엔드는 건드리지 않는다.

### B. 시그니처 — 공급사 카드

이 페이지에서 가장 중요한 결정은 공급사다. 나머지는 전부 부수적이다. 그러니
여기 한 곳에만 힘을 준다.

평범한 select 대신 **2단 카드**로 만든다. 각 카드가 담는 정보:

```
┌─────────────────────────┐  ┌─────────────────────────┐
│ ●  OpenAI               │  │ ○  Google               │
│    GPT-5.6 Luna         │  │    Gemini 3.6 Flash     │
│                         │  │                         │
│    키 등록됨            │  │    키 없음              │
└─────────────────────────┘  └─────────────────────────┘
   선택됨 — accent 테두리      비활성 — 흐림 + 키 안내
```

카드에 넣을 것은 셋뿐이다: 공급사 이름, **실제 모델명**, 키 상태.

모델명을 노출하는 이유가 있다. 사용자가 "OpenAI"만 보고는 무엇이 도는지 모른다.
`GPT-5.6 Luna`라고 적혀 있으면 그 이름으로 검색해 벤치마크와 가격을 직접 확인할 수
있다. 설정 화면이 사용자를 가두지 않는다.

키가 없는 카드는 선택 불가로 흐리게 두고, 사유("키 없음")를 카드 안에 적는다.
별도 에러 메시지를 띄우지 않는다 — 이유가 있어야 할 자리에 이유가 있으면 된다.

**키 상태 판정은 저장된 값 기준이다.** 입력 중인 값이 아니라 baseline을 본다.
타이핑 중에 카드가 깜빡이면 산만하다.

### C. Floating 저장바 (사용자 요청)

**`fixed`가 아니라 `sticky bottom-0`을 쓴다.**

스크롤 주체는 `PageScaffold`의 `div.page-scaffold`(`h-full overflow-y-auto`)이고,
콘텐츠는 그 안 `max-width: 44rem` 컬럼이다. `fixed`로 붙이면 사이드바 폭
(`--sidebar-width: 13rem`, 접히면 `4.5rem`)을 저장바가 알아야 하고, 사이드바가
접힐 때마다 위치를 다시 계산해야 한다. `sticky`는 콘텐츠 컬럼 안에 있으므로 그
계산이 필요 없다. 폭도 저절로 맞는다.

```
┌── page-scaffold (overflow-y-auto) ──────────┐
│  ┌── 44rem 컬럼 ──────────────────┐         │
│  │  헤더                          │         │
│  │  AI 공급사                     │  ← 스크롤
│  │  분석                          │         │
│  │  ...                           │         │
│  │ ┌────────────────────────────┐ │         │
│  │ │ 변경 2개  [되돌리기] [저장] │ │ ← sticky bottom-0
│  │ └────────────────────────────┘ │         │
│  └────────────────────────────────┘         │
└─────────────────────────────────────────────┘
```

**변경이 있을 때만 나타난다.** 저장할 게 없는데 바가 자리를 차지할 이유가 없다.
`hasChanges`가 이미 파생값으로 계산되고 있으니(`Settings.tsx:332-342`) 그대로 쓴다.

**변경 개수를 표시한다.** "변경 2개"처럼. 사용자가 무심코 건드린 게 있는지
확인할 수 있고, 되돌리기를 누를지 판단하는 근거가 된다. 어떤 항목인지까지는 적지
않는다 — 목록이 길어지면 바가 아니라 패널이 된다.

**스타일** — 이미 있는 `.settings-savebar`를 쓴다.

```css
.settings-savebar {
  @apply border-t border-border/80 bg-surface/95;
}
```

여기에 `backdrop-blur`를 더한다. 앱의 다른 떠 있는 표면(`toast-surface`,
`AnalysisPanel`의 sticky 헤더)이 전부 `bg-surface/9x + backdrop-blur` 조합이므로
같은 처리를 따른다.

z-index는 **20**. 이 앱의 관례상 `z-50`은 오버레이(토스트·모달·라이트박스),
`z-20`은 패널 내부 sticky다(`AnalysisPanel:1092`). 저장바는 후자에 속한다 —
토스트가 저장바를 덮어야 맞다.

**등장 모션**: 아래에서 위로 8px, 120ms, `--ease-out-strong`. 짧게 한 번만.
`prefers-reduced-motion`에서는 페이드만.

**헤더의 저장·되돌리기 버튼은 제거한다.** 같은 동작이 화면에 두 벌 있을 이유가 없다.
헤더에는 상태 뱃지만 남긴다. 보관함 경로 옆 인라인 저장 버튼(문제 2)도 함께 제거된다.

### D. 저장 후 피드백

현재는 `saved` state로 3초간 표시한다. 저장바가 사라지는 것 자체가 이미 강한
신호이므로, 여기에 토스트까지 겹치면 과하다. **토스트는 실패했을 때만 띄운다.**

성공 시: 저장바가 사라진다. 그게 전부다.
실패 시: 저장바가 남고, 그 안에 오류 사유를 적는다. 사용자가 재시도할 위치와
오류를 읽는 위치가 같아야 한다.

### E. 카피

버튼 이름을 동작 그대로 쓴다.

| 자리 | 문구 | 사유 |
|---|---|---|
| 저장 버튼 | `저장` | 짧게. "변경사항 저장"은 바 안에서 중복 |
| 되돌리기 | `되돌리기` | 기존 유지 |
| 변경 표시 | `변경 2개` | 숫자가 정보 |
| 키 없음 | `키 없음` | 상태 그대로. "설정 필요" 같은 지시형은 카드 안에서 명령조 |
| 자동 전환 토스트 | `Google Gemini로 전환했습니다` | 능동태, 완료형 |
| 키 둘 다 없음 | `API 키를 등록하면 분석을 시작할 수 있어요` | 빈 상태는 초대이지 오류가 아니다 |

### F. 접근성

- 공급사 카드는 `radiogroup` / `radio` 역할. 좌우 화살표로 이동
- 비활성 카드는 `aria-disabled`와 함께 사유를 `aria-describedby`로 연결
- 저장바 등장 시 포커스를 뺏지 않는다. 사용자는 편집 중이다
- 저장바는 `role="region"` + `aria-label="변경사항"`. 스크린리더가 건너뛰지 않도록
- 저장 결과는 `aria-live="polite"`로 알린다
- 키 입력 필드의 show/hide 토글은 기존 구현 유지

## 후속 제안 — 키 형식 검증

이번 작업 중 실제로 겪은 문제다. Anthropic 키(`sk-ant-...`)를 OpenAI 칸에 넣었는데
앱이 그대로 저장했고, 실제 호출에서야 401이 났다. 사용자도 똑같이 겪는다.

최소 대응은 저장 시 접두사 검사다(`sk-` / `AIza` 등). 더 나아가면 저장 직후 최소
요청 한 번으로 유효성을 확인해 카드에 "키 확인됨"을 표시할 수 있다. 이 설계의
공급사 카드는 그 상태를 표시할 자리를 이미 갖고 있다.

별도 태스크로 다루기를 제안한다.
