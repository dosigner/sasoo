# Sasoo 리팩토링 상세 계획과 쉬운 설명

**작성일:** 2026-11-10  
**목표:** Sasoo의 기존 분석 결과와 동작을 보존하면서, 여러 일을 한꺼번에 담당하는 코드를 역할별로 나눈다.  
**기준 문서:** [통합 계획](2026-11-09-sasoo-modular-refactor-master-plan.md), [선택한 기준선](../../validation/2026-11-09-modular-refactor-selected-baseline.md), [계약 테스트 기록](../../validation/2026-11-09-modular-refactor-contract-freeze.md).  
**기술 구성:** Electron, React/Vite, FastAPI, SQLite.  
**문서의 성격:** 앞으로 할 일을 이해하고 검토하기 위한 계획이다. 이 문서 작성으로 리팩토링이 시작되거나 완료된 것은 아니다.

**진행 갱신(2026-11-10):** R1 보고서 조립과 R3 시각화 선택 규칙 분리를 완료했다. 각 변경 전후 집중 검사와 전체 백엔드 회귀가 통과했다. [R1 검증 기록](../../validation/2026-11-10-modular-refactor-r1-report.md), [R3 검증 기록](../../validation/2026-11-10-modular-refactor-r3-visualization-policy.md)을 참고한다. R4 이후는 아직 착수하지 않았다.

## 1. 먼저, 무엇을 하려는가

리팩토링은 **사용자가 받는 결과는 유지하면서 코드의 책임과 위치를 정리하는 작업**이다. 예를 들어 지금 보고서 기능에는 논문 정보를 가져오는 일과 보고서 문장을 조립하는 일이 한 함수에 들어 있다. 이 둘을 나누면, 보고서 문장 형식만 수정할 때 데이터 조회까지 뒤져야 하는 상황을 줄일 수 있다.

예상되는 이점은 코드를 이해하고 시험하기 쉬워진다는 것이다. 다만 코드를 나누는 것만으로 분석이 더 정확해지거나, 속도가 빨라지거나, 요금 문제가 해결되지는 않는다. 그런 효과는 별도의 변경과 검증이 필요하다.

쉽게 말해 현재 일은 다음 순서다.

1. 지금 결과가 어떻게 생겼는지 기록한다. 이 작업은 상당 부분 해 두었다.
2. 한 가지 책임만 정해서 코드를 옮긴다.
3. 옮기기 전후 결과가 같은지 검사한다.
4. 통과한 뒤 다음 책임으로 넘어간다.

## 2. 지금까지 끝난 것과 남은 것

| 항목 | 현재 상태 | 뜻 |
|---|---|---|
| 기존 작업 보존 | 스냅샷 생성 | 기존 미커밋 파일을 포함한 선택 기준선을 별도 폴더에 복사했다. Git에서 무시되는 `.env`, 가상환경, 사용자 라이브러리는 제외했다. |
| 공급사 연결 차단 | 테스트용 가드 추가 | 테스트 중 Python socket의 외부 연결을 막는다. 별도 운영체제 격리도 사용했다. 자식 프로세스의 모든 시도를 가드가 집계하는 것은 아니다. |
| 비교용 테스트 | 주요 계약 고정 | 보고서 내용, 분석 단계 입력, 스키마, 시각화 계획, 인증값 등을 비교할 수 있다. 이 테스트는 현재 동작을 기록한 것이며 현재 동작이 모두 옳다는 증거는 아니다. |
| 백엔드 회귀 | R1, R3 각각 변경 전후 1,359건 통과, 7건 스킵 | 2026-11-10, Python 3.14.6 격리 복사본 기준. 실제 사용자 라이브러리와 Python 3.12 CI까지 검증한 것은 아니다. |
| 제품 코드 리팩토링 | **R1, R3 완료, R4 이후 미착수** | 보고서 조립과 시각화 선택 규칙을 분리했고 각 변경 전후 전체 백엔드 검사 결과가 같다. 아래 후속 작업은 앞으로 할 일이다. |

기준선은 **파일 스냅샷**이다. 사용자가 선택한 방식이며 기존 변경을 포함한다. 별도 commit을 만들지 않았으므로 원래 통합 계획에 적힌 깨끗한 Git HEAD 작업 트리 검증과는 다르다. 이후 작업 전에 현재 파일과 스냅샷을 다시 비교해, 그 사이 다른 변경이 생겼는지 확인한다.

## 3. 지켜야 할 규칙

- 기존 미커밋 수정, 미추적 파일, 저장된 논문, 캐시, 이전 실험 결과를 보존한다. reset, stash, 정리, 광범위한 덮어쓰기나 삭제를 하지 않는다.
- 삭제는 기존 승인 범위를 넘으면 별도 결정을 받는다. 사용자가 선택한 스냅샷 방식은 커밋 생성 승인이 아니다.
- 테스트는 별도 HOME과 앱 데이터 경로, 합성 PDF와 DB를 쓴다. 운영체제 수준에서 외부 송신을 막고 공급사 키를 넣지 않는다. 테스트용 Python 가드의 차단 횟수는 가드가 관찰한 범위의 숫자다.
- 한 묶음씩 수정하고 기존 테스트를 임의로 바꾸지 않은 상태에서 비교한다. 변경 때문에 테스트가 실패하면 원인을 확인할 때까지 다음 묶음으로 넘어가지 않는다.
- 보고서 문구, API 응답, 단계별 입력과 캐시 키, 기존 설명과 비용 기록의 의미를 유지한다. 스냅샷 테스트를 실패시킨 뒤 기대값만 새 결과로 덮어쓰지 않는다.
- 새로운 동작, 데이터 변경, 캐시 무효화, 유료 호출이 필요한 작업은 별도 설계와 사용자 결정을 거친다.

## 5. 첫 번째 상세 작업: 보고서 조립 분리 R1

### 현재 무엇이 불편한가

`backend/api/analysis_routes.py`의 `get_report`는 논문과 분석 결과를 조회하고, 결과가 없으면 오류를 만들고, 단계별 문장과 비용 합계를 조립해 응답한다. 한 함수가 여러 역할을 가져 보고서 형식만 검토하기 어렵다. 지금은 구조상의 문제를 다루며, 사용자 보고서가 틀렸다고 새로 확인한 것은 아니다.

### 어떻게 바꿀 것인가

```text
현재
보고서 요청 → 논문과 분석 결과 조회 → 보고서 문장 조립 → 응답
                모두 analysis_routes.py 안에서 처리

변경 후
보고서 요청 → analysis_routes.py: 조회와 오류 처리
             → report_service.py: 보고서 문장 조립
             → analysis_routes.py: 기존 응답 반환
```

변경 파일은 `sasoo/backend/api/analysis_routes.py`와 `sasoo/backend/api/report_service.py`다. 기존 `get_report(paper_id: int)`는 API 진입점으로 남는다. 새 `build_report_markdown(paper: dict, latest_results: dict[str, dict]) -> str`은 이미 조회된 정보로 Markdown 문자열만 만든다. 논문 조회, 분석 결과 조회, 404 응답과 `generated_at` 생성은 기존 route에 남긴다. `report_service.py`에 이미 있는 `_format_phase_data`도 유지한다.

### 무엇이 그대로여야 하나

예를 들어 어떤 논문에서 첫 단계 비용은 확인됐지만 마지막 단계 비용은 미확인이라면, 현재 보고서는 확인된 부분 합계와 미확인 단계 수를 함께 보여 준다. 분리 뒤에도 그 문구와 순서, 공백과 줄바꿈까지 같아야 한다. 미확인 비용을 0원으로 바꾸면 안 된다.

- 논문이 없을 때와 분석 결과가 없을 때의 404 메시지 두 종류.
- Screening부터 Deep Dive까지의 기존 단계 순서와 각 단계 문구.
- 실패나 부분 결과, 과거 형식 결과, 비용과 토큰이 `None`인 경우의 표시.
- `paper_id`, `title`, `markdown`, `generated_at`으로 구성된 응답 형태. 생성 시각 값 자체는 요청 시각에 따라 달라진다.
- 이미 보관 중인 사용자 논문, 결과, 파일, 비용 행. 이 작업은 DB 내용을 바꾸지 않는다.

### 실행과 확인 순서

- [x] 선택한 스냅샷과 현재 두 대상 파일 및 테스트의 차이를 확인한다. 다른 작업이 추가됐다면 그 내용을 먼저 읽고 보존한다.
- [x] 격리 복사본에서 `api/test_report_bytes_contract.py`, `api/test_report_service.py`, `api/test_analysis_routes.py`의 보고서 관련 테스트를 먼저 실행한다. 변경 전 상태에서도 실패하면 리팩토링을 시작하지 않고 원인을 기록한다.
- [x] 조립 부분을 `build_report_markdown`으로 옮기고 `get_report`에서 결과 문자열을 받아 기존 `ReportResponse`를 반환한다. 응답 형식이나 조회 경로는 바꾸지 않는다.
- [x] 기존 보고서 스냅샷과 404 테스트를 수정하지 않고 다시 실행한다. Markdown 바이트가 다르거나 `None` 비용이 0으로 표시되면 실패다.
- [x] 보고서 관련 기존 회귀와 OpenAPI 계약 테스트를 실행한다. 그다음 격리 복사본에서 `pytest services api models tools` 전체를 실행한다.
- [x] 변경된 파일, 검사 결과, 기존과 다른 점을 기록한다. 실패하면 기대값을 고쳐 통과시키지 않고 이동한 부분만 되돌릴 수 있도록 변경 범위를 분리해 둔다.

완료는 **문장 조립 책임이 분리되고, 기존 보고서와 오류 계약 및 관련 전체 회귀가 통과한 상태**다. 이 검사로 실제 논문의 과학적 정확성이나 공급사 청구를 검증한 것으로 보지는 않는다.

## 6. 그다음 작업을 조금 더 자세히

### R3, R4, R5: 분석 규칙을 나누기

- **R3 시각화 계획:** 논문에서 그림, 순서도, 대화형 화면을 어떤 순서와 개수로 만들지 정하는 코드를 분리한다. 60점과 70점 경계, 중복 항목, 그림 수 제한과 모델 선택이 바뀌면 실제 생성 건수나 비용이 달라질 수 있다. 기존 시각화 계획 스냅샷과 관련 회귀가 기준이다.

  **완료(2026-11-10):** 선택 규칙의 최상위 함수 4개(내부 보조 함수 1개 포함)와 상수 2개를 `services/visualization_policy.py`로 옮겼다. 기존 `analysis_execution` 경로에서도 같은 객체를 제공하며, 호출자와 캐시 조립은 기존 위치에 남겼다. 기존 테스트와 기대값을 바꾸지 않고 집중 366건, 전체 1,359건이 변경 전후 동일하게 통과했다. 상세 범위와 한계는 [R3 검증 기록](../../validation/2026-11-10-modular-refactor-r3-visualization-policy.md)을 참고한다.

- **R4 다이어그램과 인용:** Mermaid 문법 정리, 참고문헌 선택, 종합 결과 검사처럼 서로 다른 계산을 작은 묶음으로 차례로 옮긴다. 옮기기 전 묶음별 출력과 인용 캐시 키를 고정하고, 기존 테스트와 도구가 기존 위치를 통해 함수를 바꿔 끼우는 동작도 유지한다. 묶음별 고정이 부족하면 먼저 테스트를 보강한다.
- **R5 결과 형식:** 공급사에 전달하는 분석 결과의 구조 정의 7종을 별도 위치로 모은다. 구조 정의 한 글자 차이도 요청과 해석에 영향을 줄 수 있어, 기존 JSON 해시 7종과 완료 검사, 과거 결과 및 캐시 경로를 비교한다. R3 다음 R4, 그다음 R5 순서다.

### R7, R14: PDF 처리와 공통 지시문 정리

- **R7 PDF 시각 추출:** 첫 번째 처리 엔진이 실패할 때 다음 엔진으로 넘어가는 반복문을 따로 묶는다. 엔진 순서, 재시도 전 임시 파일 처리, 실패 시 사용량 기록과 기존 patch 경로를 보존한다. 합성 파일 목록과 테스트용 SQLite의 그림 ID, 기존 설명을 비교한다.
- **R14 공통 지시문:** 두 공급사 코드가 공유하는 기본 지시문을 중립 위치로 옮기고 예전 위치에서도 접근할 수 있게 한다. 지시문 UTF-8 해시와 두 경로의 동일 객체 검사를 유지한다. 문구를 개선하거나 캐시를 무효화하는 작업은 포함하지 않는다.

### R10, R11, R13: 화면과 앱 내부 통신 정리

- **R10 화면 출력:** 분석 화면에서 숫자와 문장을 표시하는 순수 함수를 분리한다. 현재 화면 문구와 긴 결과, 실패 상태를 그대로 유지하고 화면 테스트와 격리 Electron 화면을 확인한다.
- **R11 API 타입:** 프런트엔드에서 사용하는 데이터 모양의 정의만 분리하고 기존 import 경로에서 다시 제공한다. 타입 검사와 두 경로의 프런트 테스트를 실행한다.
- **R13 Electron 내부 통신:** 창과 백엔드 사이 요청을 처리하는 부분을 테스트 가능한 경계로 분리한다. 통신 이름, 요청에 대한 응답과 현재 발신자 확인 범위를 그대로 유지한다. 기존 HMAC 벡터, Electron 단위 테스트, 격리 앱의 인증 및 화면을 확인한다. 발신자 검증을 새로 강화하는 동작 변경은 통합 계획상 별도 승인 대상이다.

화면이나 Electron 검사는 자동 테스트만으로 끝내지 않는다. 공급사 생성 요청을 차단한 격리 앱에서 1024px와 1440px, 로딩, 오류, 취소, 키보드 조작과 콘솔을 확인하고 화면 값 하나 이상을 API와 대조한다.

### R6, R9: 상태와 저장 경계

- **R6 상태 계산:** 현재 진행률과 단계 상태를 계산하는 부분을 조회 코드에서 분리한다. 99% 상한, 취소 우선, 응답 필드와 조회 횟수를 유지한다. 다만 `planned_items`가 없는 예전 완료 논문을 어떻게 보여 줄지 사용자 결정이 먼저 필요하다. 현재 계획은 그 데이터를 `error` 또는 별도의 `legacy`로 표현하는 선택지를 제시한다. 실제 사용자 DB의 영향 범위는 아직 확인하지 않았다.
- **R9 그림과 표 저장:** 파서 파일 안의 DB 동기화와 API 변환을 분리한다. 기존 그림 설명과 ID, 파일, 오래된 자료 처리, 외부 테스트의 patch 경로를 보존한다. R7과 R8의 해당 계약 확인이 선행이며, 저장 트랜잭션을 바꾸는 작업은 이 이동에 섞지 않는다.

### R12와 추가 IPC 변경

R12는 설정 응답이 늦게 돌아왔을 때 다른 논문의 분석이 잘못 시작될 가능성을 막는 방어 코드다. 현재 앱에서는 논문을 바꾸면 작업 화면이 재생성돼 이 문제가 실제 경로에서 도달하지 않는 것으로 조사됐다. hook을 단독으로 마운트한 지연 테스트에서 먼저 재현하고, 정상 경로에서 분석이 한 번만 시작되는지도 확인한다. 이는 코드 위치만 옮기는 작업보다 동작에 가깝다.

추가 IPC 발신자 검증과 updater 동작 수정은 기존 허용 범위나 화면 표시가 바뀔 수 있으므로 R13의 단순 분리와 별도로 다룬다.

## 7. 별도 결정이 필요한 기능 작업

| 주제 | 왜 별도인가 | 결정 전에 확인할 것 |
|---|---|---|
| 실행 manifest와 fence F1 | 어느 실행이 결과를 저장했는지 기록하고, 오래된 작업의 뒤늦은 저장을 막는다. DB와 실행 경로의 동시성 의미가 바뀐다. | 기존 작업 보존, 실행 중 중복 요청, 실패와 재시작을 합성 DB로 재현하고 저장 규칙을 설계한다. |
| 요청별 비용 원장 F2-F4 | 공급사 요청별 비용, 미확인 값, 표시 합계와 예산 기준을 바꿀 수 있다. | 기존 비용 출처와 누락을 분리하고 SDK의 실제 재시도 횟수를 모의 전송으로 관찰한다. 기존 합계의 의미를 임의로 바꾸지 않는다. |
| 그림과 표 처리 F5 | 두 처리의 저장 순서와 동시 실행을 바꾼다. | 현재 실패 순서, 파일과 DB 행, 기존 설명 보존을 먼저 재현한다. |
| 개별 결함 F6 | 취소 후 polling, 중복 요청 등은 사용자가 보는 동작이나 요청 횟수가 달라진다. | 각 결함을 재현한 뒤 독립된 수정과 회귀 테스트를 준비한다. |
| 오래된 논문의 상태 F7 | 과거 완료 논문을 어떤 상태로 보여 줄지 제품 선택이 필요하다. | 실제 데이터 분포는 미확인임을 밝히고, 표시 선택지와 화면 영향을 제시한다. |
| 캐시 무효화 F8 | 기존 캐시가 새 지시문과 맞는지 판정하는 키를 바꾸면 공급사 재호출이 발생할 수 있다. | 영향 범위와 예상 비용을 먼저 확인한다. 미확인 비용을 0으로 가정하지 않는다. |
| 문서 정정 F9 | 기존 프로젝트 지침의 명시 내용을 변경한다. | 실제 CI 및 스크립트와 비교한 정정안을 검토받는다. |

3단계 DB 및 실행 조율은 manifest 설계가 확정되기 전에 시작하지 않는다. 오래된 작업자의 지연 쓰기, 동시 실행, 취소 후 commit, 그림 성공 후 표 실패, 재시작, 채팅 스트림 중단 등의 현재 동작을 먼저 합성 환경에서 고정한다.

## 8. 각 단계가 끝났다고 말할 수 있는 조건

1. 정한 범위의 코드만 바뀌고 기존 미커밋 변경과 데이터가 보존됐다.
2. 변경 전 실패가 있으면 먼저 원인을 기록했고, 해당 묶음의 집중 테스트와 마지막 수정 뒤 관련 전체 회귀가 통과했다.
3. 화면이나 앱 내부 통신을 만졌다면 별도 격리 Electron에서 실제 화면과 오류 상태도 확인했다.
4. 결과가 달라졌다면 이유를 설명하고 승인된 동작 변경인지 확인했다. 예상하지 못한 차이나 외부 연결은 중단 사유다.
5. 각 보고서에 검증한 환경과 검증하지 못한 환경을 구분한다. Python 3.12 CI와 Windows, 실제 사용자 DB, 실제 공급사 응답 및 청구, 패키징 앱은 별도 증거가 나오기 전까지 미검증이다.

특히 현재 OpenAPI 전체 스냅샷은 FastAPI 0.141.1, Pydantic 2.13.5에서 만들어졌다. 프로젝트 의존성은 하한만 지정된 항목이 있으므로, Python 3.12 CI에서 실패하면 코드 변경과 프레임워크 버전 차이를 구분해 조사한다. 스냅샷을 무조건 덮어쓰지 않는다.

## 9. 용어 풀이

- **기준선:** 변경 전 결과를 비교하기 위해 보관한 현재 상태.
- **계약 테스트:** API 응답, 문장, 파일처럼 바뀌면 안 되는 결과를 고정한 검사.
- **스냅샷 테스트:** 정해진 입력의 결과를 미리 저장한 결과와 비교하는 검사.
- **캐시:** 이전 분석 결과를 다시 사용해 요청을 줄이는 저장값. 캐시 키는 같은 결과를 재사용해도 되는지 구분하는 값이다.
- **격리 환경:** 실제 계정과 데이터에 영향을 주지 않도록 별도 폴더와 모의 데이터를 쓰는 실행 환경.
- **manifest:** 특정 실행의 신원과 어떤 결과가 그 실행에서 나왔는지를 기록하는 실행 명세. 현재 완성된 기능이라고 가정하지 않는다.
- **fence:** 오래된 작업자가 새 실행의 결과를 덮어쓰지 못하게 하는 세대 확인 장치.
- **legacy:** 현재 형식이 만들어지기 전에 저장된 예전 자료.

**검증 관점의 핵심:** 문장을 만드는 위치를 옮겨도 결과가 같다는 검사와, 분석이 과학적으로 옳다는 검사는 서로 다르다. 전자는 이번 리팩토링의 기본 조건이고, 후자는 원문 근거와 별도의 평가가 필요하다.
