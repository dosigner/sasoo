# Sasoo 1.0.1 상세 요약과 읽기 GUI Implementation Plan

> **For agentic workers:** When implementation is requested and required approvals are satisfied, execute task-by-task using an available workflow. Prefer superpowers:subagent-driven-development or superpowers:executing-plans when available; otherwise use an equivalent workflow with the same approval gates. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 요약만 읽고 문제, 작동 원리, 결과와 한계를 설명할 수 있게 하며, 바이오와 로보틱스의 ‘옮겨 쓸 때 확인할 조건’과 읽기 GUI를 함께 제공한다.

**Architecture:** 기존 심층 분석 JSON에 `section_answers`와 `transfer_checks`를 추가하고 같은 생성 결과를 요약과 읽기 안내에서 재사용한다. 기존 여섯 요약 필드, API와 DB 저장 형태, 읽기 안내의 독립 생성 및 캐시를 유지한다. GUI는 기존 `PhaseSection`, `Markdown`, 인용 연결과 디자인 토큰을 확장한다.

**Tech Stack:** 현재 저장소의 Electron, React 19, TypeScript, Vite 8, Tailwind CSS 4, react-markdown 10, KaTeX, rehype-highlight, FastAPI, pytest, Vitest/jsdom. lockfile의 설치 버전을 기준으로 구현하며 라이브러리를 업그레이드하는 작업은 포함하지 않는다.

**Spec:** [상세 요약과 읽기 GUI 최종 명세](../specs/2026-09-22-v1.0.1-summary-and-reading-design.md). 콘텐츠 계약, 화면 도식, Before/After, 글자 크기, 상태와 완료 기준을 포함하므로 구현자는 두 문서를 함께 읽는다.

## Global Constraints

- 2026-09-22 구현 요청으로 실행 단계에 진입했다. 체크박스는 실제 검증 결과에 따라 갱신한다. 유료 검증은 별도 비용 확인을 거치며 원격 공개는 하지 않는다.
- 목표 수준은 B다. 개인 실험실 또는 로봇 설정 비교, 자동 실행, 임상 적용 판단은 포함하지 않는다.
- 기존 여섯 요약 필드와 `comparison_scope = in_paper_only`를 유지한다. `as_is`, `to_be`만 선택 필드로 둔다.
- 새 JSON 배열은 필수 키이며 빈 배열을 허용한다. `section_answers` 최대 12개, `transfer_checks` 최대 8개, 각 `source_refs` 최대 4개다.
- 심층 분석 출력 상한은 16,000 tokens다. 마지막 schema property는 기존 배열 `practical_applications`로 유지한다.
- 자동 분석 단계를 추가하지 않는다. 읽기 안내는 명시적 생성과 재생성, 캐시 재사용을 유지한다. 조회와 탭 이동은 생성 요청 0회다.
- 새 근거는 절 제목, 그림, 표로 연결한다. 인쇄 페이지와 PDF 파일 페이지를 새로 혼용하지 않는다.
- 구형 결과와 사용자 데이터는 삭제하지 않는다. 재분석 확인과 비용 안내는 기존 흐름을 사용한다.
- Pretendard, 굵기 400/500/650, 기존 색상과 radius 6/12/pill을 사용한다. 전역 폰트 크기와 테마를 변경하지 않는다.
- 앱 기본 1400×900, 최소 1024×680을 유지한다. 새 본문 기본값은 15px/26px이며 root 16px 기준의 rem으로 구현한다.
- 기존 공동 작업을 보존한다. 현재 미추적 상태인 2026-09-07 paper-experiment 명세와 계획은 이 작업의 수정 대상이 아니다.

- [x] **Step 2: 독립된 schema 상수와 작은 검증 함수를 구현한다.**

`SectionAnswer`, `TransferCheck` 필드는 명세 §3.2와 정확히 일치시킨다. object의 모든 명명 필드는 required, `source_refs`는 string 배열이다. 최상위의 두 배열에 `maxItems`를 표현하고 런타임에서도 개수를 검증한다. provider가 JSON schema 제한을 모두 강제한다고 가정하지 않는다.

```python
from collections.abc import Mapping

_SUMMARY_FIELDS = {"section_answers", "transfer_checks"}

def validate_summary_extensions(
    data: Mapping[str, object], *, require: bool = False,
) -> bool:
    if "_parse_error" in data or "error" in data:
        raise ValueError("심층 분석 응답 형식을 확인하지 못했어요")
    present = _SUMMARY_FIELDS.intersection(data)
    if not present and not require:
        return False
    if present != _SUMMARY_FIELDS:
        raise ValueError("요약 확장 필드가 누락됐습니다")
    rules = {
        "section_answers": (12, ("section_title", "question", "answer", "explanation")),
        "transfer_checks": (8, ("item", "paper_condition", "check_before_transfer")),
    }
    for name, (maximum, fields) in rules.items():
        entries = data[name]
        if not isinstance(entries, list) or len(entries) > maximum:
            raise ValueError(f"{name} 배열 형식 또는 항목 수가 잘못됐습니다")
        for entry in entries:
            if not isinstance(entry, dict):
                raise ValueError(f"{name} 항목이 객체가 아닙니다")
            for field in fields:
                value = entry.get(field)
                if not isinstance(value, str) or (field != "explanation" and not value.strip()):
                    raise ValueError(f"{name}.{field} 문자열이 잘못됐습니다")
            refs = entry.get("source_refs")
            if not isinstance(refs, list) or len(refs) > 4:
                raise ValueError(f"{name}.source_refs 배열이 잘못됐습니다")
            if not all(isinstance(ref, str) and ref.strip() for ref in refs):
                raise ValueError(f"{name}.source_refs 출처가 잘못됐습니다")
            if name == "section_answers":
                if not refs:
                    raise ValueError("핵심 답변에 출처가 필요합니다")
            else:
                basis = entry.get("condition_basis")
                if basis not in ("reported", "inferred", "not_reported"):
                    raise ValueError("적용 조건의 근거 성격이 잘못됐습니다")
                if basis != "not_reported" and not refs:
                    raise ValueError("명시 또는 추론 조건에 출처가 필요합니다")
    return True
```

이 함수는 데이터를 잘라내거나 원래 심층 분석 키를 제거하지 않는다. 최상위 root가 object인지는 호출부에서 먼저 검사한다. schema 상수에도 같은 키, 타입과 required 규칙을 표현하고 테스트로 계약 차이를 확인한다.

- [x] **Step 4: 저장 전 새 응답을 검사하고 실패를 관찰 가능하게 만든다.**

`json.loads` 뒤 root가 object인지 확인하고 `validate_summary_extensions(payload, require=True)`를 호출한다. 실패는 기존 `_parse_error` 오류 결과와 phase `error` 흐름으로 연결하되, 메시지는 ‘심층 분석 응답 형식을 확인하지 못했어요’로 구문/구조 오류 모두를 설명한다. 실패 응답도 기존 tokens, cost, model 기록을 남긴다. 추가 LLM 보정 호출을 만들지 않는다. 구형 캐시를 조회하는 경로에 `require=True`를 넣지 않는다.

- [x] **Step 5: 정상/빈 배열/누락/과다/오류/캐시를 검증한다.**

테스트 입력은 정상 두 배열, 둘 다 빈 배열, 한 배열 누락, object 대신 list인 root, 잘못된 enum, 문자열 대신 숫자, 13개 답변, 9개 조건, 5개 출처, 구형 저장 결과다. `_run_deep_dive`의 mock 모델 호출로 구조 오류가 완료 처리되지 않고 비용 기록은 남는지 검증한다. 16,000 상한과 마지막 속성 잠금 테스트를 유지한다.

**완료 산출물:** 기존 한 번의 심층 분석 호출이 검증 가능한 확장 JSON을 생성하고, 잘못된 형식을 성공으로 저장하지 않는다.

실행 근거: 구조/스키마/분석 경로 224개와 하위 검사 4개, provider 검사 70개와 하위 검사 7개 통과. 기존 테스트 기대값은 유지했다. 실제 코드에서 provider 완료 상태가 전달되지 않고 공통 JSON 복구가 잘린 결과를 살릴 수 있음을 확인하여 `services/llm/openai_client.py`, `gemini_client.py`와 해당 테스트를 추가 수정했다. 심층 분석은 incomplete 응답을 재호출하거나 복구하지 않고 오류로 기록하며 사용량을 보존한다. 다른 단계의 복구 동작은 유지한다.
