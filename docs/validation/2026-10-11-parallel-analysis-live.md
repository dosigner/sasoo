## 원문에 근거한 내용 비교

독립 검토자는 실행 방식과 시간/비용을 모르는 상태에서 A/B 두 답변을 원문 PDF와 대조했다. 판정 후 공개한 mapping은 A=순차, B=병렬이다.

- 둘 다 deep_dive 필드 17개(coverage 포함), 절별 답변 12개, 적용 조건 검사 8개를 유지했다. 주요 분석 포인트 집합이 같았다.
- Table 1/2의 주요 NLL/FID/NFE 및 초해상도 지표가 원문과 일치했다.
- CFM/FM gradient 동등성의 전제, conditional OT와 marginal OT의 차이, 생성할 때 ODE가 필요하다는 구분을 보존했다.
- 종합 결과의 수식은 순차 5개, 병렬 4개 모두 원문과 일치했다. 60% NFE를 60% 절감으로 오기하지 않았다.

확인한 보완 사항은 다음과 같다.

| 분류 | 관측한 문제 | 영향 |
|---|---|---|
| 두 방식 공통, 중요한 누락 | recipe에 원문 p.17의 pixel 변환 `x/128−1`과 likelihood/BPD 보정, 특히 `+7`이 빠짐 | NLL 재현 계산에 영향 |
| 순차, 중요한 오류 | 시간 sampling을 미보고처럼 서술하지만 원문에 `t ~ U[0,1]`이 명시됨 | 재현자가 시간 분포를 임의로 정할 수 있음 |
| 병렬, 설명 누락 | 25% 더 큰 모델이라는 효율 비교 조건이 synthesis evidence에만 있고 자체 설명에서는 약함 | 33% 이미지 처리량 비교의 조건 전달 부족 |
| 공통 metadata | `has_figures=false`와 실제 시각 분석의 17개 그림, 표 metadata 1개와 본문 Table 1–4 설명이 불일치 | 단계별 입력/추출 metadata와 원문 전체 내용을 구분해야 함 |

33%는 원문이 보고한 누적 학습 이미지 처리량의 반올림 비교값이다. 초당 처리량이나 실제 학습 시간의 단축률이 아니다. 두 출력은 장단점이 서로 달랐으며, 한 번씩의 출력으로 품질 동등성이나 일반적 우열을 확정하지 않는다.

자세한 원문 페이지와 JSON 위치는 [블라인드 품질 검토](assets/parallel-live-20261011/quality-review.md)에 있다. 원본 실응답은 그대로 보존했다.

## 생성 그림과 HTML

그림 파일의 생성 성공과 과학적 내용의 정확성을 따로 확인했다.

- 순차 그림 2는 Gaussian density 식의 좌변을 `ψ_t`로 표기해 flow map과 density `p_t`를 혼동했다. 명백한 표기 오류다.
- 순차 그림 4는 수치 비교를 요청했지만 실제 그림에서 수치가 빠지고 범례/표식만 반복됐다.
- 병렬 구조 그림 1의 marginal vector field 식은 conditional field와 density ratio를 여러 줄로 쌓아 곱셈 관계가 모호하다. 잘못된 분모라고 단정하지 않지만 표준 수식처럼 명확하게 읽히지 않는다.
- 병렬 그림 2/3은 학습의 conditional target과 생성 입력을 구분하고, conditional OT가 marginal OT 최적성을 뜻하지 않는다는 설명을 유지했다.

[그림 수식 독립 검토](assets/parallel-live-20261011/image-addendum.md), [그림 목록](assets/parallel-live-20261011/visual-artifacts.json)에 연결했다. 그림의 식을 구현에 옮길 때는 원문 또는 검증한 텍스트 수식을 사용해야 한다.

병렬 실행에서 생성된 OT 계산기는 독립적인 Python 대수 계산과 화면 출력 4개 사례를 대조했다. 상대 오차는 `5e-7` 이내였고, 벡터 차원 불일치, σ_min=0, 범위를 벗어난 t를 거부했다. 390px 화면에서 가로 넘침, 런타임/콘솔 오류, 외부 요청은 없었다. **빈 t는 거부하지 않고 0으로 처리하는 결함이 있었다.**

계산기의 속도는 설명에 명시된 대로 고정 위치 `x=x0`에서의 Eulerian field를 평가한다. `x0=0, x1=1, σ_min=0.1, t=1`에서 표시값 10은 그 정의에서는 맞다. 이동 궤적 `x=ψ_t(x0)`에서의 속도는 1이므로, 이를 같은 값으로 읽으면 안 된다. 앱의 자동 실행 검사는 원문 수치/모델 검증을 대신하지 않는다.

[HTML 검산 결과](assets/parallel-live-20261011/html-evidence.json), [검산 코드](assets/parallel-live-20261011/verify_generated_html.py), [생성 원본](assets/parallel-live-20261011/generated-interactive.html)을 보존했다. 검증에서 실패한 입력을 숨기거나 원본을 고쳐 통과시키지 않았다.

## 설치형 앱과 실제 프로세스

기존 `/Applications/Sasoo.app`이 없어 별도 검증용 앱을 만들었다. Python 3.12.13으로 백엔드를 패키징했고 주요 의존성 버전은 작업 환경과 맞췄다([버전 목록](assets/parallel-live-20261011/packaging-pins.txt)). 실제 앱의 `app.isPackaged=true`, 버전 1.2.2, `file:` UI 로딩과 번들 백엔드의 인증된 API 응답을 확인했다.

설치 경로: `/Users/dongj/Applications/Sasoo Parallel Validation 20261011.app`. 사용자 라이브러리 대신 검증용 DB/문서 복사본을 사용했다. API 응답을 mock하지 않았고 실제 공급자 키는 주입하지 않았다.

- 1400/1024 크기에서 PDF, 분석 내용, 생성 이미지 3개, Mermaid, sandbox HTML을 확인했다. 그림은 실제 파일을 읽었고 HTML t=1의 화면 출력도 독립 검산과 일치했다.
- UI에서 실제 분석 API를 호출한 캐시 재분석은 약 1.80초에 완료됐다. 실제 번들 워커가 생성됐고, 7개 단계의 캐시 적중, 신규 생성 결과 행 0개, `running 99 → completed 100` 전환을 확인했다.
- 별도 Python 워커 2개를 실제 프로세스로 실행하고 기존 stale reconciliation/claim 경로로 generation을 1→2로 교체했다. 이전 워커는 종료 코드 75, 새 워커는 0으로 종료했다. 이전에 저장한 첫 결과는 재사용했고, 이전 워커의 늦은 두 번째 저장은 0회였다.

워커 교체 실험의 생성기 응답은 제어 가능한 테스트 응답이다. 프로세스, SQLite, heartbeat, generation 검사와 결과 저장은 실제 구현을 사용했다. 실제 API에서 강제로 프로세스를 죽여 유료 결과를 유실시키지는 않았다.

## 실제 요청을 보낸 뒤 취소

이미지 HTTP request body 송신 완료를 확인한 뒤 `_render_image`를 기다리는 task를 취소했다. 로컬 대기는 취소됐지만 공급자 작업은 약 **13.19초 더 진행**되어 이미지를 반환했다. 그동안 render semaphore 슬롯은 점유된 채 유지됐고, 실제 작업이 끝난 뒤 반환됐다. 최종 응답 사용량의 계산 비용은 **$0.042015**였다.

즉, 슬롯 보호 구현은 실제 요청에서도 동작한다. 클라이언트 task 취소는 이미 발행된 생성 요청이나 과금의 취소를 뜻하지 않는다. 이 실험은 공급자 사용량 반환을 확인한 것이며 실제 결제 청구서 검증은 아니다.

[실제 취소 증거](assets/parallel-live-20261011/live-cancel-evidence.json), [재현 코드](assets/parallel-live-20261011/verify_live_cancel.py), [프로세스 종료 확인](assets/parallel-live-20261011/process-cleanup.json)을 남겼다.

학습 메모: 병렬화 검증에는 실행 중첩, 저장/취소, 생성 내용의 정확성을 각각 확인해야 한다. 실제로 빨라졌다는 관측과 그 차이의 원인을 분리하고, 렌더 성공과 원문 정확성을 분리하는 원칙을 재사용할 수 있다. 원장의 요청 시각, 원문 페이지, 실제 앱 출력으로 결과를 재검산할 수 있으며, 계획 항목 수나 서버 캐시가 다른 두 실행을 동일 작업량의 속도 비교로 해석하는 것이 주요 함정이다.
