# 그림 자세히 읽기 지연 개선

그림 설명을 SSE로 표시하고, 같은 그림의 진행 중 생성 작업을 재사용한다. 기존 JSON API도 같은 작업을 기다린다. 완료된 설명은 기존 DB 캐시를 사용한다.

## 변경

- 프론트에서 설명을 수신하는 즉시 표시한다. 생성 중에는 상태를 표시하고, 실패한 부분 설명은 미완료임을 알린다.
- 프론트는 논문 ID와 그림 ID로 요청을 공유한다. 서버도 같은 키로 생성 작업을 공유한다. 창을 닫아도 서버 생성은 계속되며, 다시 연결하면 기존 부분 설명부터 받는다.
- 프롬프트의 여섯 상세 항목은 유지한다. 같은 결과의 반복 서술을 줄이고, 관련 수치, 조건, 패널별 차이, 불확실성은 보존하도록 지시한다. 원문 근거와 관측, 해석을 구분하고 미확인 내용을 표시하도록 지시한다.
- 공통 지침, 본문 문맥, 분석 결과와 정렬된 그림 캡션을 개별 그림 정보와 이미지 앞에 둔다. OpenAI에는 공통 문맥 끝의 `prompt_cache_breakpoint`와 `prompt_cache_options.mode=explicit`을 전달한다. Gemini 입력에는 OpenAI 전용 필드를 넣지 않는다.
- 응답에 캐시 읽기/쓰기 토큰을 포함해 적중 여부를 확인할 수 있게 한다. 모델과 사고량은 변경하지 않는다.
- 완료 신호, 사용량 또는 설명 본문이 없거나 응답이 미완료이면 DB에 저장하지 않는다. 부분 설명이 이미 표시된 뒤에는 기본 사고량으로 자동 재호출하지 않는다.

OpenAI의 명시적 캐시 경계 동작은 [공식 프롬프트 캐시 문서](https://developers.openai.com/api/docs/guides/prompt-caching)를 기준으로 구현했다. 실제 적중은 최소 입력 길이, 캐시 보존과 공통 입력의 동일 여부에 따라 달라진다.

## 검증

- 백엔드 `pytest services api models -q`: 1,077개 테스트, 231개 하위 검증 통과.
- 프론트 `pnpm test`: 33개 파일, 322개 테스트 통과.
- `pnpm tsc --noEmit`, `pnpm build`, `pnpm lint` 통과.
- 스트리밍 부분 수신, 진행 중 작업 공유, 독자 연결 종료, 완료 결과 재사용, 즉시 재시도, 완료 신호/사용량 누락과 Gemini 완료 ID 검증을 확인했다.
- SDK mock에서 OpenAI 캐시 모드와 공통 문맥 경계가 이미지 앞에 전달되는지 확인했다.
- 실제 FigureGallery 컴포넌트를 Aside Browser에서 1400×900과 1024×680으로 실행했다. 제어 가능한 SSE 테스트 응답을 사용했다.
- 첫 그림 열기, 다음/이전 이동, 창 닫기/다시 열기 동안 첫 그림의 HTTP 요청과 생성은 각각 1회였다. 두 번째 그림은 의도적인 오류 후 재시도해 각각 2회였다.
- 완료 전 부분 설명과 생성 중 상태, 오류와 미완료 안내, 재시도 후 완료 상태를 확인했다. 완료 후 생성 중 표시는 사라졌고 브라우저 오류는 없었다. 표시된 `10 ms`, `2 V`가 테스트 응답과 일치했다.
- 1024×680에서 긴 부분 설명을 수신한 뒤 실패시키고, 오류 안내와 스크롤 아래의 재시도 버튼에 접근할 수 있는지 확인했다. 패널 높이는 528 px, 전체 내용 높이는 2,234 px였으며 내용이 잘리지 않았다.
- [GUI 검증 데이터](assets/figure-speed-20261007/gui-check.json)와 같은 폴더의 스크린샷을 보존했다.

관련 자동 검증 재현:

```bash
cd sasoo/backend
./.venv/bin/python -m pytest api/test_figure_stream.py services/llm/test_openai_client.py api/test_analysis_routes.py -q
cd ../frontend

```

## 검증 범위

유료 API 호출, 원논문을 대상으로 한 변경 전후 시간 비교와 설명 정확도 비교, 실제 캐시 적중률 측정은 실행하지 않았다. 설치된 Electron 앱의 재패키징도 포함하지 않는다. 서버 작업 공유는 현재 단일 백엔드 프로세스 범위이며, 다중 worker로 확장하면 영속 작업 claim이 필요하다.

스트리밍의 개선 대상은 읽기 시작 시간이다. 전체 생성 시간의 변화는 출력 길이와 모델 처리에 달려 있고, 입력 캐시는 출력 생성 과정을 생략하지 않는다.
