# 병렬 분석 후속 작업 우선순위

2026-10-11. 사용자의 요청은 추가 작업 파악이다. 실제 제품 수정이나 새 API 호출은 하지 않고, 저장된 실응답과 현재 코드를 대조했다. 기존 Graphify 연결도는 9월 25일 자료이므로 탐색에만 사용하고 아래 판단은 현재 소스로 확인했다.

## 확인한 원인

| 발견 | 원인과 근거 | 판단 |
|---|---|---|
| 숫자가 없는 비교 그림 | `_generate_single_paperbanana`가 recipe/deep_dive 앞 1,800자씩과 visualization_input 앞 2,200자만 전달하고, `_plan_description`에서 다시 6,000자로 제한한다. 해당 실요청에는 2.99/6.35/142가 없었고 설명 모델은 수치가 없으니 18개 칸을 비워 두라고 답했다. | 필요한 원문 표를 다음 단계에 전달하지 않은 문제를 먼저 해결해야 함 |
| `ψ_t=Gaussian density` 그림 | 해당 식이 이미지 모델에 전달하기 전 설명 모델의 응답에 이미 존재했다. | 설명 작성 단계의 과학적 오류와 이미지 렌더 오류를 따로 검사해야 함 |
| HTML이 기획 문장에 의존 | `_generate_single_html`은 체인을 이어받지 않는 독립 요청이다. 원문 입력은 이미 4,200자로 제한된 visualization_input이고 실요청에는 해당 식의 원문 구간이 없었다. | 식/변수 정의/평가 위치를 근거와 함께 전달할 필요 |
| recipe의 원문 조건 누락 | recipe는 앞선 PDF 체인을 이어받는다. 이 실험의 누락을 단순한 본문 잘림 탓으로 단정할 수 없다. 기존 `verify_recipe_parameters`는 이미 출력된 parameters만 검사한다. steps/missing_info의 주장이나 아예 빠진 항목은 검사하지 않는다. | 인용 정확성에 더해 재현 조건의 누락과 미보고 판정을 검토해야 함 |
| 빈 시간 입력 통과 | 생성 코드가 `Number('')`를 0으로 처리했다. 앱 검사기는 숫자/슬라이더의 경계/중간값을 주로 시험하며 빈 값은 넣지 않는다. | 생성 입력 검증과 앱의 검사 범위 모두 보완 필요 |
| 그림/표 metadata 불일치 | screening은 5,000자 입력으로 has_figures를 추정한다. visual의 tables_found는 저장 직전 추출 DB 행 수로 덮어쓴다. | 원문 전체의 개수와 추출한 개수가 섞인 의미 문제. DB 행을 임의로 늘려서는 안 됨 |
| `60%%` | `formatMetricValue`가 값에 단위가 이미 포함돼 있는지 확인하지 않고 붙인다. | 공통 formatter에서 고칠 수 있는 표시 결함 |

## 권장 실행 순서

### 1. 비용 없는 표시/검사 결함과 회귀 기준부터 고정

- 단위 중복은 `formatMetricValue`에서 처리한다. 숫자와 단위의 의미를 유지하고, 원본 저장값은 바꾸지 않는다.
- 필수 숫자 입력의 빈 문자열, 공백, 유효 범위 밖 값과 vector 입력의 차원 불일치를 검사한다. 선택 입력의 기본값은 명시적으로 구분한다.
- HTML 검사에서 입력별 출력 변화 또는 의도된 불변을 확인한다. 단순히 문서의 어느 한 부분이 바뀌었다는 사실을 모든 입력의 정상 동작으로 일반화하지 않는다.
- 검사 문구는 실행 점검과 원문/수치 검증의 범위를 계속 구분한다. 수학적으로 상수인 정상 출력까지 오류로 판정하지 않는다.
- 그림/표 개수는 “추출한 개수”라는 현재 사실을 명확히 표시한다. 일부 본문으로 추정한 `has_figures=false`를 논문 전체에 그림이 없다는 확정값으로 사용하지 않는다.

대상: `frontend/src/lib/synthesisBlocks.ts`, `components/HtmlVisualization.tsx`, 해당 테스트, backend visual/screening 출력과 report/UI 소비처.

완료 기준: 기존 `60% + %` fixture는 `60%`로 표시된다. 빈 필수 t를 0으로 계산하는 기존 HTML fixture는 통과 처리되지 않는다. 원문 개수와 추출 개수를 혼동하는 화면/보고서가 없으며, 기존 캐시와 원본 실응답은 유지된다.

### 2. 그림/HTML의 원문 근거 전달을 고침

- 계획이 참조하는 표, 수식, 변수 정의, 적용 조건을 기존 문서 context와 PDF 근거에서 찾아 해당 생성 요청에 함께 전달한다. 앞부분 문자열만 자르는 현재 입력 구성을 교체한다.
- 출처가 없는 수치를 모델에게 채우게 하지 않는다. 필요한 원문 수치를 확보하지 못한 정량 그림은 그 이유를 남기고 생성을 보류한다.
- 확인한 표의 값과 식을 설명 모델이 다시 만들어 쓰지 않도록, 고정할 과학적 내용과 그림의 배치 설명을 구분한다.
- 정확한 수식은 기존 `EquationChain`의 KaTeX 렌더 경로를 우선 활용한다. 이미지는 구조/연결/상태 설명을 담당하도록 구성한다. 수식을 이미지에 반드시 포함하는 항목은 설명문과 최종 이미지 양쪽을 점검한다.
- HTML은 독립 변수, 파생 변수, 식의 평가 위치를 명시한다. `u_t(x0)`와 `u_t(ψ_t(x0))`처럼 서로 다른 계산이 섞이지 않아야 한다.

대상: `backend/services/analysis_execution.py`의 `_generate_single_paperbanana`, `_generate_single_html`, `document_context.py`, `viz/figure_gen.py`의 `_plan_description`. 기존 원문/근거 도구와 renderer를 재사용한다.

완료 기준: 저장된 Table 1 사례의 새 요청 payload에 필요한 수치와 원문 위치가 포함된다. 빈 칸을 지시하는 설명이나 `ψ=p` 혼동을 그대로 생성 성공으로 승격하지 않는다. HTML의 고정 위치/이동 위치 조건과 경계값을 별도 계산으로 대조한다. 논문 고유 상수는 제품 코드에 하드코딩하지 않는다.

### 3. recipe에 재현 조건 누락과 미보고 판단 검사를 추가

- 기존 분석 포인트와 상세 설명은 유지한다.
- 전처리/정규화, 입력 분포와 sampling, 학습 target/loss, 평가식과 단위 보정, solver/허용오차를 분야에 맞는 재현 점검 항목으로 다룬다. 해당 없는 항목을 억지로 생성하지 않는다.
- `missing_info`에 들어갈 주장은 원문에서 해당 내용을 확인하지 못했다는 상태와 저자가 명시하지 않았다는 판단을 구분한다. 원문에 실제 있는 항목을 미보고로 단정하는 충돌을 잡는다.
- 기존 인용/페이지/값 검사기는 유지한다. 파라미터 근거가 맞다는 사실과 레시피 전체가 완전하다는 주장을 구분한다.
- Flow Matching 회귀 fixture에 `t~U[0,1]`, `x/128−1`, density/BPD 보정과 `+7`, 학습 target, 미보고 σ_min을 함께 넣는다. 제품 로직은 다른 논문에도 적용 가능한 조건으로 작성한다.

대상: `_run_recipe`의 지시/출력 계약, `evidence_verifier.py`와 `evidence_repo.py`의 적용 범위, recipe 검증 테스트. 처음부터 매 분석마다 새 검토 모델을 호출하는 구조를 추가하지 않고 현재 단계와 검증 경로에서 해결 가능한 범위를 먼저 구현한다.

완료 기준: 원문에 있는 재현 조건이 누락되거나 “미보고”라고 분류되면 검증에서 드러난다. σ_min/학습 seed처럼 실제 확인되지 않은 값은 임의로 채우지 않는다. 기존 17개 deep_dive 필드, 12개 절별 답변, 8개 적용 조건 검사는 이 회귀 사례에서 유지된다.

### 4. 수정본만 통제된 비교로 재검증

- 먼저 저장된 실패 사례로 오프라인 회귀 검사를 끝낸다.
- 속도 비교에서는 두 실행에 같은 시각화 계획과 항목 수, 입력/모델/effort를 사용한다. 순차→병렬과 병렬→순차 순서를 모두 포함하고 공급자 캐시 사용량을 별도로 기록한다.
- 계산 중심, 실험/정량 중심, 절차가 없는 리뷰 논문을 포함한 작은 대표 묶음으로 품질을 확인한다. 이 정도 표본으로도 전체 오류율이나 동등성을 확정하지 않는다.
- 원문 검토는 실행 방식/시간/비용을 가린 상태에서 수행한다. 이미지 생성 성공, HTML 실행 성공, 원문 수치 정확성은 각각 기록한다.
- 기존 요청 ID와 성공 결과는 재발행하지 않는다. 새 수정본의 검증은 별도 실행 ID/예산/원장으로 구분한다.

완료 기준: 동일 작업량에서의 구간별/전체 시간과 비용을 비교할 수 있고, 위에서 발견한 실패 사례가 새 결과에서 해결됐음을 원문으로 확인한다. 해결하지 못한 사례는 남긴다.

## 변경 범위와 캐시

표시/로컬 검증 수정은 기존 결과를 다시 생성하지 않고 적용한다. 프롬프트나 근거 입력이 바뀌는 단계는 해당 입력/검증 버전이 캐시에 반영돼야 한다. 전역 `_CHAIN_CACHE_VERSION`을 무조건 올려 모든 기존 분석을 다시 실행하는 방식은 피한다. 새 결과 생성은 명시적인 재분석 경로에서 수행하며, 이전 실험과 비용 기록을 보존한다.

권장 작업 묶음은 **작은 표시/검사 수정 → 그림/HTML 근거 전달 → recipe 누락 검사 → 수정본 비교**다. 사용자 승인 전제의 새로운 배포 계획이나 모델 교체는 이번 파악 범위에 추가하지 않았다.
